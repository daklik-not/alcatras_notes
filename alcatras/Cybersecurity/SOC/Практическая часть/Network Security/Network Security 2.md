Перед началом атаки, атакующим нужно понять, что им атаковать - discovery
Сначала злоумышленник попытается максимально изучить все что открыто в публичный интернет - DMZ. Он пытается узнать, информацию о том, к каким ассетам можно получить доступ, IP, OS, сервисы, их версии - уязвимости версий

Стоит добавить, что средства защиты также часто проводят похожие сканы - например чтобы проверить, не запущена ли какая-то ненужная программа, или открыт лишний порт, убедиться, что вся активность документируется

Отсюда возникает проблема - как отличать хорошие сканы от плохих.
1. Сделать так, чтобы местные сканеры или внешние не вызывали алерты. Это немного опасно, поскольку взлом сканера позволит злоумышленнику незаметно сканировать
2. Интегрировать TI

***External Scanning***
Скан с внешнего IP.  Чаще всего свидетельствует о том, что атака находится в стадии *Разведки - Reconnaissance*. Самый просто способ устранения - блокировка по IP. Однако злоумышленник может вернуться с другим IP.
**Internal Scanning Activity**
Сканирование внутри сети. Свидетельствует о том, что атака находится в стадии *Discovery*. Требует глубокого анализа
![[Cache/Pasted image 20260703011718.png]]

**Horizontal Scanning**
Сканирование 1 порта у множества IP. Полезно, например, когда ищется уязвимость в конкретном приложении, которое имеет стандартный порт, который оно слушает. Легко идентифицируется по одинаковому *src IP* и одинаковому порту, но разных адресах
**Vertical Scanning**
Сканирование множества портов по 1 IP. Полезно для получения  *отпечатка* хоста и идентификации того, какие уязвимости можно использовать.


#### Механизмы сканирования
Вообще это тесно связано с заметкой по nmap. Мб я потом привяжу ее
**Ping** - самый простой тип - просто показывает в онлайн хост или нет. Очень часто блокируется в современных сетях.
**TCP SYN** - TCP соединение инициируется трехсторонним рукопожатием. Это достаточно скрытый скан, его сложно обнаружить. Также он дает понимание о том открыт ли порт
***UDP Scan*** - посылаем пустой UDP пакет. Если порт закрыт, то по-идее назад должен вернуться ICMP пакет. Однако если он не вернется, то это не говорит о том, что данные дошли - хост может быть просто оффлайн, или Firewall заблочил
Внутренние сканы надо исключать

#### Обнаружение эксфильтрации данных
Неавторизованная передача данных от организации на внешний адрес назначения.
Данные могут быть проданы, можно потребовать у компании деньги за возврат, данные могут пригодиться для установления *persistence*, нанесения урона репутации компании
Типичные стадии относящиеся к эксфильтрации - *Discovery, Collection, Staging, Compression, Exfiltration transport, C2*.

***Техники и индикаторы***
Большое количество данных, проходящих через firewall/proxy, высокая энтропия выходящих данных(то есть случайность данных), длинные DNS запросы, подозрительные процессы, активность в cloud storage API.

#### DNS  Tunneling
DNS лукапы часто разрешены файрволлами, поэтому их легко можно предотвратить. Запросы выглядят как обычные DNS запросы, пока не взглянешь поближе. Данные можно закодировать поддомены или TXT запросы.
```c
Здесь вставить скрипт атаки - после того как сделаю руму
```
***Индикаторы атаки***
1. Множество DNS запросов посланы на 1 и тот же внешний домен
2. Длинные имена поддоменов
3. Высокая энтропия, паттерны Base64 кодирования
4. Редкие типы записей - TXT, NULL - много TXT ответов
5. Много NXMODAIN(введенного адреса несуществует)
6. Интервальность запросов

#### FTP Data Exfiltration
Аналогично здесь я просто не знаю FTP поэтому плохо понимаю, как он работает - надо как-нибудь изучить FTP
FTP один из самых старых протоколов для передачи данных по сети.
Злоумышленники используют 
1. легитимные FTP сервера(публичные или неправильно сконфигурированные)  для передачи данных.
2. Используют скомпрометированные  пользовательские данные
3. Используют нестандартные порты или туннелирование

Нужно смотреть на 
1. USER, PASS 
2. повторяющиееся STOR, RETR
3. Открытые каналы, открытые на эфемерных портах, спаренные с большими пэйлоадами

Примеры в Wireshark

```c
ftp.request.command == "USER" || ftp.request.command == "PASS" //поиск учетных данны
ftp || ftp-data // исключаем контрольные пакеты
ftp contains "csv" // файл содержит csv
ftp && frame.len > 90 // длинные фреймы
```

#### Data Exfiltration via HTTP
Эксфильтрация данных через HTTP используется, поскольку HTTP трафик легко обфусцировать и он легко смешивается с остальным веб-трафиком. 
1. POST запросы на внешние сервера или облачные хранилища
2. GET запросы с закодированными данными - например в хэдерах
3. Эксфильтрация маскируется под загрузку на популярные сервисы 
4. Данные помещаются в заголовок
5. Данные передаются в нескольких запросах
6. TLS шифрование - не всегда удобно или возможно дешифровать трафик. Приходится смотреть на метаданные или SNI(типо заголовок Host но в TLS рукопожатии передается)

**Индикаторы**
1. Необычно большие HTTP POST запросы на странные хосты
2. HTTP запросы на домены с низкой репутацией или редкие для стандартного workflow
3. Частые маленькие запросы
4. Разделенные передачи, где множество запросов задают большой файл

Вообщем после выполнения трафика наверное стоит добавить, что проверять придется практически все гипотезы, поскольку может быть примерно что угодно - эксфильтрация не особо заметна новичку

#### Data exfiltration via ICMP
Есть несколько техник
1. Данные кодируются в ICMP пэйлоады. 
2. Кастомные ICMP коды
3. Фрагментация и реассемблирование
4. Шифрование

**Индикаторы**
1. Постоянные ICMP сессии на внешний хост
2. Большой или частый ICMP с пэйлоадом
3. Данные с высокой энтропией - для проверки энтропии файла можно использовать функцию ent в Linux CLI
4. От этого хоста дальше не идут никакие данные


### MITM Detection
Злоумышленник находится между эндпоинтами и модифицирует или перенаправляет трафик
Атака разбивается на 2 стадии
1. *Interception(внедрение)* - атакующий встраивает себя в поток взаимодействия , эксплуатируя уязвимости в протоколах - ARP, DNS, IP спуфинг
2. Атакующий модифицирует взаимодействие.

***Стандартные типы MITM атак***
1. Сниффинг пакетов  - ловим незашифрованные пакеты в сети, часто на открытом Wi-FI
2. Подделка сессии - использование сессионных токенов, чтобы выдавать себя за другого
3. SSL стриппинг - понижение HTTPS до HTTP
4.  Отправка данных на неправильный адрес, через манипулирование DNS ответом
5. Создание фейковых сетей, чтобы перехватывать пользовательский трафик

Если классифицировать по CyberKillChain, то MITM атака относится к 
1. Exploitation. А если конкретнее, то перехват сессии, например, с помощью ARP или DNS.
2.  Installation. После перехвата сессии, злоумышленник может легко подменить данные, которые запрашивает клиент


#### Detecting ARP spoofing
ARP сопоставляет IP на MAC адрес в локальной сети.
Сама атака довольно примитивна. Просто злоумышленник посылает фейковый ARP пакет, чтобы обмануть устройства. В результате ARP кэш отравляется.
**Индикаторы**
1. Дуплицированные MAC-IP. Множество MAC на 1 IP
2. Большое число ARP ответов без запросов
3. Большое количество ARP трафика
4. Необычная маршрутизация
5.  Множество запросов типа Who has 192.168.1.x? Tell 192.168.1.y
```c
arp.opcode == 1 // ARP requests
arp.opcode == 2 // ARP response
arp.isgratuitous // "приветственные" ARP. Они не отвечают на какой-то конкретный запрос, а создаются по собственной инициативе.
eth.src == 02:aa:bb:cc:00:01 // MAC адрес отправителя на канальном уровне
arp.src.proto_ipv4 // IP адрес отправителя в ARP пакете
```

### DNS Mitm
Суть атаки также достаточно примитивна.  Хост отправляет DNS запрос, который перехватывается, и хосту назад отправляется фейковый IP с которым он будет работать. Злоумышленник должен уже находиться в локальной сети. 
**Индикаторы**
1. Несколько DNS ответов на 1 и тот же запрос
2. DNS ответ от странного источника 
3. Маленький TTL. Это важно, поскольку злоумышленнику важно уметь часто перенастраивать сессию, например, если IP DNS сервера заблокировали firewall.
4. Незапрашиваемый DNS ответ

#### MITM SSL Stripping
Атакующий перехватывает или модифицирует трафик , чтобы убрать или предотвратить TLS шифрование между клиентом и сервером. Из-за этого клиент общается по HTTPS а не по HTTPS. Атакующий сохраняет HTTPS сессию с сервером, пока общается по HTTP с хостом.
**Как оно работает**
1. Хост инициализирует HTTPS запрос к вебсайту 
2. Атакующий перехватывает запрос используя ARP спуфинг или захват шлюза. 
3. Атакующий подключается к сайту по HTTPS, но общается с клиентом по HTTP.

**Индикаторы**
1.   Изначальный запрос идет на порт 443, остальные на порт 80
2.   HTTP Status code 301, 302 - редиректы, которые направляют HTTPS запрос на HTTP ресурс
3.  Ошибки сертификатов - неудачный TLS handshake - хотя обычно он спрятан.
4. Является следствием ARP, DNS спуфинга -> можно посмотреть их
```c
tls.handshake.type == 1 && tls.handshake.extensions_server_name == "corp-login.acme-corp.local" // client hello
```
