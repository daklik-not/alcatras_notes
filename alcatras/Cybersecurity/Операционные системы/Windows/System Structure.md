#### Структура операционной системы
Центральный слой -  само NTOS ядро. Оно загружается с файла ntoskrnl.exe при запуске Windows. NTOS состоит из 2 слоев - **executive**, который содержит большинство сервисов и **kernel**, который реализует планирование потоков, абстракции синхронизации,  в том числе реализацию прерываний, trap, и так далее.

На самом верху, на самом деле в пользовательском слое есть библиотека ntdll.dll. Когда процессу нужен доступ к ядру он использует функцию оттуда. Библиотека мапится в адресное пространство процесса(оно рандомно выбирается при запуску компьютера) а обьект section(аналог mmap) может быть использован любым процессом для обращения к библиотеке

#### Kernel layer
Есть 2 слоя ядра *kernel* и *executive*. Главная абстрация это потоки, и все что связано с их управлением, например создание и уничтожение структур, отвечающих за потоки. Планировщик потоков(не процессов) ядра должен убедиться, что состояние, программные счетчик и все остальные состояния потоков были успешны сохранены. Если потоки из разных процессов, то нужно менять АП.
Ядро дает 2 типа механизма синхронизации:
	1. *Control objects* - структуры данных, которое kernel layer предоставляет как абстрацию для executive layer.  Они аллоцируются executive, но при этом управляются рутинами из kernel. Например к ним относятся DPC. обрабатывают все остальное отличное от обьектов диспетчера.  Все остальное
	2. Dispatcher objects - обычные обьекты синхронизации - мьютексы, семафоры и так далее. 

#### Deferred Procedure Calls
Control objects помимо примитивных вызовов  реализует ***DPC(Deferred Procedure Calls)***. DPC обьекты были созданы, чтобы уменьшить количество времени, которое тратится на ISR.
IRQL - приоритет прерывания в системе. DIRQL - приоритет устройства. 
Когда процессор выполняет ISR, его текущий IRQL равен DIRQL устройства. На этом уровне процессор **маскирует все прерывания с IRQL ≤ DIRQL**. То есть другие устройства с таким же или меньшим приоритетом не могут прервать процессор. Если ISR будет долго обрабатывать данные, другие устройства не смогут получить обслуживание вовремя. Это приводит к задержкам, потерям данных и падению пропускной способности.
Если ISR выполняется слишком долго, то обработка низкоприоритетных прерываний будет задержана, что может привести к потерям данных.  Поэтому ISR выполняет только то, что нельзя отложить - подтверждение прерывания, сохранение результата операции. После этого ISR ставится в очередь DPC. 
Объект DPC представляет из себя то, что осталось доделать и kernel layer ставит этот обьект в список DPC для конкретного процессора. DPC не выполнится никогда, пока есть хоть 1 ISR на обработку.
Возникает вопрос - если прерывания идет непрерывно, то DPC просто не будет выполняться? Этого не происходит потому что 1) ISR очень короткий 2) устройство не генерирует прерывания непрерывно 3) устройство может копить прерывания.
После того, как не осталось ISR в очереди, ядро регистрирует запрос к железу через программное прерывание, которое создает (неожиданно) *HAL*, чтобы прервать процессор с приоритетом 2 (*DISPATCH LEVEL*).   После этого ядро обрабатывает все DCP обьекты, которые может, насколько я понимаю, пока не придет следующее ISR
Пример нажатие кнопки на клавиатуре. Ты нажимаешь на кнопку, ISR клавиатуры читает, какая кнопка была нажата, после чего оно не обрабатывается а откладывается в DPC. 
DPC используется для запуска рутин, которые срабатывают по timer interrupt.  Чтобы не блокировать потоки, событие таймера, которое запущено длительное количество времени, запрашивается пул рабочих потоков ядра. 
ISR и DPC не должны выполняться долго, поскольку пока они запущены на процессоре, на нем ничего больше не может быть запущено.  Если они блокируют потоки - **DPC Storms**, у Windows есть защитный механизм **DPC Watchdog**.  Он при превышении своих лимитов инициирует *system crash*, с кодом DPC_WATCHDOG_VIOLATION и информацией о длинном DPC. 
Также планировщик потоков  ядра Windows имеет свой механизм защиты. Для каждого недавнего DPC он хранит историю выполнения и таким образом определяет *long-running DPC*.  Когда такие DPC запущены на процессоре, поток, который был запущен на этом же процессоре перепланируется на другом процессоре. 

#### Asynchronous Procedure Calls
Еще 1 обьект  управления ядра.  Он выполняется в контексте отдельного потока. 
DPC ничего не знает о потоке. Он просто записывает в буфер ядра - обращается к IO системе, уведомляя о том, что IO операция завершена.  Далее IO система запрашивает запуск APC чтобы запустить в контексте потока, который создал изначальный запрос на чтение, чтобы оно могло писать в его userspace. 
Есть **kernel APC.** Он берет данные, положенные в буфер ядра DPC, запускается в контексте потока(стек ядра потока), и копирует эти данные в пользовательское адресное пространство потока(чаще всего в кучу процесса). kernel APC выполняется, когда поток на процессоре
Есть **User APC**.  Он необязателен, и может быть вызван только у потоков, которые явно ждут его - такое состояние называется **alertable wait**.  Когда User APC вызывается(насколько я понял, будет ли она вызвана или нет зависит от того, какая функция чтения была вызвана), де-факто происходит callback в код, определенный user APC. Этот код выполняется полностью в пользовательском пространстве.
**Пример:**
ReadFileEx (или WriteFileEx) []. В её параметрах вы обязаны явно передать указатель на функцию-колбэк (так называемую FileIOCompletionRoutine) [].
Есть **Special User-mode APC's**. Они отличаются тем, что могут выполняться даже тогда, когда поток, у которого они выполняются находится не в *alertable wait* состоянии. 
APC механизм может быть использован для того чтобы безопасно принудительно завершать потоки.  Чтобы случайно принудительно не завершить поток, который, например удерживает мьютекс, поток должен объявить что он находится в критическом регионе. Тогда APC отложится.  Поток безопасно завершается - освобождает системные ресурсы, вызывает процедуры очистки - де-факто самоликвидируется.
