На картинке показаны слои Windows OS. Помимо GUI слоев есть программные интерфейсы, на которых она строится. По большей части это коды библиотек - dll, которые программа динамически линкует, чтобы получить что-то от ОС. Некоторые из них - **client библиотеки**, которые используют ***RPC*** чтобы общаться с сервисами ОС в другом процессе. Здесь RPC это не удаленные вызов в прямом смысле.

![[Pasted image 20260710170432.png|697]]
Сердце Windows - процесс ntoskrnl.exe. Он предоставляет интерфейсы, поверх которых строится вся остальная операционная система - системные вызовы. Поверх этого процесса в пользовательском пространстве находятся **subsystems**. Например тот-же WSL(современный WSL это отдельная виртуальная машина, так что это не совсем правильно). Их смысл в том, чтобы переводить системные вызовы например POSIX в вызовы понятные ntoskrnl.exe.
Сейчас Windows приложения написаны , используя API,  которые построен поверх Win32 подсистемы - например **WinRT API**.  Также есть такая штука - language projection. Короче проектор, просто внутри себя  сопоставляет каждый вызов к библиотеке с вызовом к WIN API, и вызывает
Короче так не очень понятно наверное, на картинке ниже видно

#windows_chain 
```
Приложение (C#) 
    ↓ (вызов выглядит как родной C#)
Language Projection (C#/WinRT) 
    ↓ (превращает C#-вызов в WinRT-COM-вызов)
WinRT API (реализация на C++) 
    ↓ (превращает в Win32 API)
kernel32.dll (Win32) 
    ↓ (превращает в Native API)
ntdll.dll 
    ↓ (syscall)
ntoskrnl.exe (ядро)
```

Есть несколько подходов к написанию Win приложений
1. C++ с использованием Win32 API.  Используется системными программистами, когда нужен максимальный контроль надо всем.
2. C++, WinRT. WinRT предоставляет удобное ООП API для работы с Windows.
3. C#, .NET -классический подход. .NET представляет из себя обьекты/блоки кода, которые значительно упрощают написание кода + управляемая среда исполнения(например меньше следить за памятью).
