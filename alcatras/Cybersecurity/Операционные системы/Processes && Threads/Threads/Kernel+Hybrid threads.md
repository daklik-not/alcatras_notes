**Реализация потоков в ядре**
В таком подходе ядро знает о потоках и управляет ими. Thread table теперь находится в ядре ОС.  При создании вызывается kernel call. Thread table содержит регистры, состояние и другую информацию. Соответственно в ядре хранится и PCB процесса. Все вызовы, блокирующие поток реализованы как системные вызовы - это намного дороже, чем вызовы к runtime системе. Очевидно дорого каждый раз удалять с создавать потоки - системы с kernel потоками часто переиспользуют потоки, поток после завершения не удаляется, а просто помечается неактивным. Мультипрограммирование реализуется с помощью прерываний
Есть и проблемы. Например не решается проблема наследования при создании. Что должен делать новосозданный поток, копировать стек или нет и так далее. Также в классической модели процессов сигналы посылаются процессам. В таком случае непонятно, какой поток должен обработать сигнал. Например на Linux сигнал обрабатывается любым потоком, то есть выбирается рандомно, однако мы можем заблокировать сигналы на всех потоках кроме одного.

Есть несколько гибридных потоков - в каждом гибридном несколько пользовательских потоков.
Возникает вопрос - а как именно в таком случае потоки блокируются?
При блокировке - блокируется поток ядра, однако пользовательские потоки, которые могут быть выполнены достаточно легко привязываются к другому потоку ядра.
Примерный код внутри runtime системы

```
// Упрощенная схема работы
void runtime_scheduler() {
    while (true) {
        for (each kernel_thread in thread_pool) {
            if (kernel_thread.state == BLOCKED) {
                save_context(current_user_thread);         
                user_thread* next = get_ready_user_thread();
                bind_to_kernel_thread(next, free_kernel_thread);
            }
        }
    }
}
```
