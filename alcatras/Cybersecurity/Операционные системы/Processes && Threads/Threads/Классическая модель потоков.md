**Классичесская модель потоков**
Модель процессов базируется на 2 независимых концептах - группировка ресурсов и выполнение. У процесса есть свое адресное пространство, которое содержит текст программы, и данные и другие ресурсы. Ресурсы могут содержать открытые файлы, дочерние процессы, обработчики сигналов и т.д. 
За концепт выполнения отвечает **поток**.
У потока есть программный счетчик, который отвечает за то, какую инструкцию выполнить следующей. У него есть регистры. У него также есть стек. Важно отметить, что в современных системах такого понятия, как стек процесса впринципе не существует. Есть только стек главного потока процесса, но он эквивалентен всем остальным потокам процесса. Все, что относится к тому, как проходит прерывание процессов относится к потоку. За 1 маленьким исключением - если потоки которые сменяют друг друга лежат в 1 процессе, то сохранение на PCB не происходит. Фактически PCB состоит из множества **TCB - Thread Control Block**. В нем хранится информация о потоке, например указатель на стек ядра потока(как уже описывалось в прерывании процессов).

Между потоками нет никакой защиты в плане разделения памяти. Фактически то, как взаимодействуют между собой потоки внутри процесса не очень сильно волнует OS. Реализовывать механизмы вроде взаимного исключения разработчики должны сами.
Как и процесса, у потока есть есть 4 состояния - запущен, готов, заблокирован, завершен.
Как я уже уже писал у каждого потока есть свой стек. Каждый стек потока содержит один фрейм для каждой процедуры, которая запущена, но еще не завершена. 
Обычно процессы запускаются с 1 потоком. Поток может создавать новые потоки - thread_create. Иногда между потоками есть иерархия, но чаще всего ее нет. Когда поток завершается - thread_exit. Thread_join - поток ждет завершения какого-то другого потока. Thread_yeild - добровольная передача управления процессором другому потоку. Полезно в пользовательских потоках, когда система не понимает, когда надо менять потоки -> нужно давать другим потокам шанс на запуск
С потоками есть свои проблемы. Допустим процесс вызывает fork(). Не очень понятно, как новосозданный процесс должен наследовать потоки. В каждом дизайне операционной системы используются различные подходы. Например на Linux - fork создает только 1 поток в ребенке. В стандарте POSIX есть pthread_atfork() -> она позволяет добавлять процедуры, которые произойдут после создания процесса(например создание новых потоков)
Также возникают проблемы с памятью - например первый поток выдяляет память - thread swith - второй поток также выделяет память -> память выделена дважды.
