Когда нет необходимости в способности семафора считать доступные ресурсы, как, например в producer-consumer проблеме, может быть использована более простая версия семафора - **mutex(мьютекс)**. Они нужны для реализации взаимного исключения к какому-то разделяемому ресурсу или куску кода. Они полезны в пользовательских потоках, когда нужен быстрый механизм ограничения доступа.
Важный факт - межпроцессные мьютексы почти никогда не нужны, они очень медленные.
Теперь немного отойду от книги.
Как я понял, существуют мьютексы ядра и пользовательские мьютексы. 
1. Kernel mutex - нужны для реализации блокировок в коде самого ядра, условно говоря потоки программ самого ядра операционной системы. Это другой уровень реализации, который нужен только системным программистам
2. Userspace mutex - то, что будет в этой заметке. Когда потоки используют быстрые высокоуровневые механизмы и атомарные операции для реализации мьютексов. Не используются системные вызовы и другие дорогостоящие системные операции.
$mutex\_lock$ входим в критическую секцию
$mutex\_unlock$ освобождаем критическую секцию
$mutex\_trylock$ попытается войти в критическую секцию и если не получится, не заблокируется, а вернет сообщение об ошибке. Это дает потоку возможность самому решать, что делать дальше.
Ниже приведен пример кода мьютекса для (важно) пользовательских потоков:
```
mutex_lock:
    TSL REGISTER, MUTEX     | Копируем mutex в регистр и устанавливаем mutex = 1
    CMP REGISTER, #0        | Проверяем, был ли mutex = 0?
    JZE ok                  | Если был 0 (свободен), переходим к ok
    CALL thread_yield       | Mutex занят; вызываем планировщик для переключения потока
    JMP mutex_lock          | Пытаемся снова после возвращения
ok:
    RET                     | Возврат; критические секция захвачена

mutex_unlock:
    MOVE MUTEX, #0          | Записываем 0 в mutex
    RET                     | Возврат к вызывающей стороне
```
Почему только для пользовательских? Потому что thread_yeild в потоках ядра не имеет смысла, поскольку там рано или поздно поток сам поменяется благодаря мультипрограммированию и прерываниям. 
Еще, хотя здесь фактически не используется spinlock, тем не менее, проверка на то, был ли мьютекс равен 0 происходит циклично, каждый раз, когда потоку возвращается управление. Это не есть хорошо.

Есть проблема с процессами, когда 2 процессам нужен семафор или мьютекс. В таком случае он может хранится в самом ядре, и доступ к нему осуществляется только через системные вызовы.

**Mutexes in Pthreads**
Phtreads предоставляет множество функция для синхронизации потоков. Стандартный механизм использует mutex переменную, которая может быть заблокирована или разблокирована. Реализация мьютексов зависит от операционной системы - в Linux - futexы, в Windows - WaitOnAddress. Если мьютекс уже заблокирован, вызывающий поток блокируется, до разблокировки. Если множество потоков ждут освобождения мьютекса, когда он разблокирован, только один из них может разблокировать. Правильной реализацией синхронизации и взаимного исключения занимается программист.
