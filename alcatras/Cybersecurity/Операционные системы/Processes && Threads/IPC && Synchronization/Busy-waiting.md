**Mutual Exclusion with Busy Waiting**
**Interrupt Disabling**
Можно просто отключить прерывания, пока 1 процесс находится в критическом регионе. Есть 2 проблемы. Нельзя давать пользовательским процессам такую власть - если он не выйдет из критического региона, то это будет конец всей системы. Во-вторых на современных мультипроцессорных системах, это заблокирует прерывания только на 1 ядре, пока остальные будут работать. Однако такой подход может использоваться самой операционной системе на однопроцессорных системах - например, когда ядру нужно обновить переменные или критические списки(например списки памяти для выделения).
**Lock variables**
Попробуем чисто программное решение. Установим **lock** переменную. Если она равна 1, то процесс просто ждет, пока другой не выйдет из критической секции и не установит ее значение на 0. Однако это не работает. Процесс может зайти, далее произойдет прерывание, второй процесс тоже зайдет. Таким образом, уже 2 процесса в памяти. Очевидно, что такие ситуации будут возникать в любом случае.
**Strict alternation(строгое чередование)**
```
while (TRUE) {
    while (turn != 0) { } /* loop */
    critical_region();
    turn = 1;
    noncritical_region();
}

while (TRUE) {
    while (turn != 1) { } /* loop */
    critical_region();
    turn = 0;
    noncritical_region();
}
```
Буквально идея в том, чтобы просто чередовать процессы. Один процесс будет висеть в бесконечном цикле, пока другой не завершит свою работу, потом третий ждет второго, и так по кругу. Во-первых это очень медленно - если 1 процесс выполняет очень долгую работу, другой будет так же долго ждать, вне зависимости от того, нужна ли ему критическая секция или нет. То есть - если первый выполнил всю свою работу в некритической секции, то он будет ждать пока второй не закончит работу в критической секции(а это может быть очень долго).
PS: Блокировка, которая использует busy waiting называется **spin lock**
**Peterson's solution**
```
#define FALSE 0
#define TRUE 1
#define N 2                   /* number of processes */

int turn;                     /* whose turn is it? */
int interested[N];            /* all values initially 0 (FALSE) */

void enter_region(int process)  /* process is 0 or 1 */
{
    int other;
    other = 1 - process;        /* number of the other process */
    interested[process] = TRUE; /* show that you are interested */
    turn = process;             /* set flag */
    while (turn == process && interested[other] == TRUE) /* null statement */ ;
}

void leave_region(int process)  /* process: who is leaving */
{
    interested[process] = FALSE; /* indicate departure from critical region */
}
```
Первое нормальное решение проблемы взаимного исключения. Однако есть нюанс - работает только для 2 процессов. Рассмотрим пример - первый процесс висит в цикле, ждет пока нулевой закончит, $turn = 1$, потом приходит второй процесс и устанавливает $turn = 2$.  Теперь первый процесс просто не сможет выйти из цикла - бесконечный цикл процесса. Поэтому, очевидно, оно не подходит для современных систем. Ключевое отличие от строгого чередования в том, что процесс, который хочет в критическую секцию, не будет ждать, пока второй процесс не закончит свою не критическую секцию - сразу пойдет в критическую.
**TSL**
Теперь обратимся к аппаратному обеспечению. Инструкция TSL читает memory word(машинное слово) lock на регистр RX, и затем сохраняет новое значение на то же слово. Все эти операции не могут быть прерваны прерыванием - CPU, выполняющей TSL инструкцию блокирует шину памяти. Тут какой-то неприятный ассемблкод - но в целом комментарии все описывают.
```
enter_region:
    TSL REGISTER, LOCK      ; Атомарно: копируем LOCK в REGISTER и устанавливаем LOCK=1
    CMP REGISTER, #0        ; Проверяем, был ли LOCK равен 0?
    JNE enter_region        ; Если не 0 (заблокировано), повторяем цикл
    RET                     ; Возврат: вход в критическую секцию выполнен

leave_region:
    MOVE LOCK, #0           ; Записываем 0 в LOCK (разблокировка)
    RET                     ; Возврат к вызывающей программе
```
Вроде бы все идеально, но такая штука все еще медленная из-за JNE - которая фактические представляет из себя просто цикл на повторение.

**Problems**
У активного ожидания есть значительные проблемы. Во-первых постоянный цикл постоянно сьедает процессорное время на проверку. Во вторых, рассмотрим ситуацию - один процесс с низким приоритетом, другой с высоким. Низкий находится в критической секции, происходит прерывание, теперь высокий хочет зайти в критическую секцию. Он не может зайти в нее, поскольку низкий в критическом сегменте, а низкий не может выйти, потому, что он не может запуститься, пока запущен высокий. Это называется -- **priority inversion problem**
