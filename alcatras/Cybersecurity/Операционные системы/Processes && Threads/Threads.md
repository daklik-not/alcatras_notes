У каждого процесса есть адресное пространство и один поток контроля. Однако часто необходимо, чтобы в одном адресном пространстве было запущено сразу много потоков.
Причины для существования потоков.
1. В большинстве приложения в 1 момент времени происходит сразу много событий. Потоки постоянно блокируются, разблокируются, потом снова блокируются. Грубо говоря разбиение какого-то количества заданий между потоками.
2. Потоки намного быстрее процессов.
3. Производительность . Потоки позволяют пересекаться дополнительным IO и вычислениям.
4. Потоки полезны на мультипроцессорных системах
Рассмотрим пример веб-сервера.
На большинстве сайтов к каким-то страницам доступ запрашивается чаще чем к другим. Веб-серверы используют это, сохраняя наиболее часто обращаемые страницы в RAM. Такой подход называется **кэшированием**.
Есть 1 поток - **диспетчер (dispatcher)**. Он считывает запросы из сети.  После этого он выбирает исполнителя - **worker thread** и передает ему сообщение, чаще всего через указатель. Далее диспетчер будит спящего рабочего переводя его из заблокированного состояния в готовое
Далее рабочий проверяет, можно ли удовлетворить запрос из кэша. Если нет, запускается read операция и поток блокируется до завершения операции диска.
Это происходит так, потому что чтением занимается не сам поток а DMA, чтобы облегчить нагрузку на процессор. В этот момент диспетчером выбирается другой рабочий поток

Программы диспетчера и рабочего:
```
while (TRUE) {
	get next request(&buf);
	handoff work(&buf);
	//код потока диспетчера
}

while (TRUE) {
	wait for work(&buf)
	look for page in cache(&buf, &page);
	if (page not in cache(&page))
	read page from disk(&buf, &page);
	return page(&page);
	//код потока рабочего
}
```
Еще пример когда программе нужно обработать большое количество данных. Обычный подход - прочитать данные, выполнить над ними какие-то действия, и затем записать снова. Если доступны только блокирующие системные вызовы(на потоки), то процесс блокируется, пока данные входят или выходят. Процессор просто простаивает. В таком случае процесс может быть структурирован, как input thread, processing thread, output thread.  Очевидно,что если системный вызов заблокирует весь процесс, а не только 1 поток, то ничего не получится(PS такое может произойти, если польностью пользовательская реализация потоков).

**singlethreaded - multithreaded**
	Возникает проблема с глобальными переменными. Например errno. Сначала один поток меняет ее значение, затем thread switch другой поток читает ее и тоже получает ошибку, хотя для него нет никакой ошибки. Одно из решений такой проблемы не считая радикальных(запретить глобальные переменные) -> дать каждому потоку собственные глобальные переменные. Такой подход называется  **Thread Local Storage**.
	Грубо говоря TSL - это область памяти обычно на куче процесса, которую может изменять только соответствующий ей поток
	
Для изменения глобальных переменных используются:
	 create_global("buffptr")  - выделение памяти для глобальной переменной на куче процесса
	 set_global("bufptr", &buf) - сохраняет значение ссылки в буфер
	 read_global("buf_ptr") - возвращает адрес, сохраненный в глобальной переменной
	 PS: Таненбаум имеет в виду  глобальные переменные для одного потока, то есть переменные, которые видны всем функциям в одном потоке. Errno - это глобальная переменная процесса. С ней такой подход работать не будет.
На практике TSL используется примерно так:
```
#include <pthread.h>
#include <stdio.h>
static __thread int thread_counter = 100; // для всех потоков
void* thread_func(void* arg) {
    int id = *(int*)arg;
    printf("Поток %d: начальное значение = %d\n", id, thread_counter);
    thread_counter += id * 10;
    printf("Поток %d: после изменения = %d\n", id, thread_counter);
    return NULL;
}
int main() {
    pthread_t t1, t2;
    int id1 = 1, id2 = 2;
    printf("Main: начальное значение = %d\n", thread_counter);
    pthread_create(&t1, NULL, thread_func, &id1);
    pthread_create(&t2, NULL, thread_func, &id2);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("Main: после завершения потоков = %d\n", thread_counter);
    return 0;
}
```
Есть проблема с тем, что некоторые вызовы из библиотеки процедур сделаны так, что если они будут прерваны, то нет возможности их восстановить и надо делат ьвсе заново. Аналогичная проблема с обновлением списков malloc.
Важная проблема с обновлением стека. У каждого потока есть свой собственный стек. Расширением стека потока занимается ядро системы. А если потоки в пользовательском пространстве? Непонятно как расширять в таком случае
