Реализация для поток значительно отличается в зависимости для того, какие потоки мы используем
**User-level threads**
Ядро не знает о потоках. Так как нет аппаратных прерываний этот поток будет оставаться запущенным так долго, как ему хочется. Если он использует весь квантум процесса, ядро выберет другой процесс для запуска. Он каждый раз при запуске процесса будет забирать у него весь квант времени. Тем не менее, он никак не будет влиять на другие процессы. И наоборот, если потоки краткие и завершаются до завершения своего кванта времени, то они будут делать $thread\_yeild$. Чаще всего используется round-robin и priority scheduling. Единственная проблема, что нет прерываний по таймеру - потоки не знают когда меняться. Но, поскольку руководство потоками это задача не системы, а программиста - это не страшно. Для таких систем программист должен четко прописывать системные вызовы **thread_yeild** для того чтобы один поток не забирал себе все время.
User-level потоки могут использовать application-specific планировщик. Вспомним веб-сервер. Есть 1 поток диспетчер, 1 заблокированный рабочий и 2 незаблокированных рабочих. Если планировщик специально сделан для веб-сервера, то он запустить диспетчер, чтобы тот запустил готовую работу. Ядро же просто не может быть так узко-специализированно - посколько во-первых переписывание кода ядра плохая практика, во-вторых ядро старается угодить всем системам(очевидно, что есть серверные ОС, а есть десктопные - здесь про то, что сервера тоже разные совсем бывают),
**Kernel-level threads**
В этом случае ядро напрямую меняет потоки. Важно сказать, хоть в учебнике этого нет, process switch происходит, когда вызываются потоки из разных процессов. Такж у потоков ядра меняется стек, program counter, и другие данные, о которых написано в заметке о kernel-level threads.  Потокам также выделяется квантум времени.
Большая разница в производительности. В user-level threads нужно просто выполнить несколько машинных инструкций. В kernel-level - полная смена контекста, смена memory map и инвалидация кэша(если поток из другого процесса).
Когда ядро знает, что смена  потоков из разных процессов очень дорогая операция, она может использовать это для планирования. Например, если есть 2 одинаково важных потока, каждый из которых принадлежат разному процессу, то выполнится тот поток, который находится в текущем.
