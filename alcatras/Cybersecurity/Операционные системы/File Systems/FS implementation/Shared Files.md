### Shared Files 
Иногда пользователи хотят разделять файлы. Тогда получится структура, как на картинке.
Теперь граф ФС - не дерево, а ДАГ.

Если в архитектуре ОС директории содержат адреса файла на диске, то когда один пользователь добавляет новый блок к файлу, структура у другого сама по себе не обновляется. Решение этой проблемы заключается в том, чтобы хранить адреса блоков диска не в директории, а в структуре данных ядра - i-node, в большинстве случаев. Это подход **hard linking**.  Есть проблемы. Когда C удаляет файл, i-node не удалится, поскольку на него есть ссылки, но при этом владелец не сменится - нет легкого способа узнать откуда жестко ссылаются на этот файл. В итоге мы получим i-node, который в RAM, но ни на что не ссылается, причем B не знает об этом. Единственное что можно сделать, удалять вхождение в директорию у юзера C, но при этом не трогать сам i-node. Но на деле это такой себе подход, поскольку владельцем все еще остается C.

Есть другой подход - **symbolic linking**.  Пользователь B может прилинковаться  к файлу пользователю C - ОС создает специальный файл типа LINK, и записывает его в директорию B. Этот файл содержит только нужный путь. Когда B читает из такого файла, ОС видит тип файла, ищет имя этого файла и читает его. У символических ссылок есть несколько плюсов - во-первых, так можно связать файлы по сети. Во-вторых, проблема, описанная для hard linking здесь не возникает - если владелец убирает файл, то все попытки других пользователей обратится по символической ссылке вызовут ошибку, но при этом удаление файла типа LINK вообще никак не повлияет на реальный файл. Тем не менее у символических ссылок свои проблемы - накладные нагрузки. Сначала нужно прочитать файл LINK, затем, получив путь, спуститься по пути в нужную папку, и только потом прочитать файл оттуда.  У LINK файла нужно не просто прочитать i-node, если путь длинный, то его еще надо прочесть с диска, с отдельного блока.

У всех ссылок есть проблема - при бэкапе файлы будут копироваться в нескольких экземплярах.
