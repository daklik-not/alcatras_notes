#### Files Implementation
Диск разбит на блоки - типичный размер - 4КБ. Блок - единица работы с диском,  ОС не может загрузить байты, только блоки.  Для чего нужны блоки? Файлы размером 500 байт читаются почти так же быстро как и 4КБ. Таким образом увеличивая размер единицы информации мы резко сокращаем количество обращений к диску, что есть хорошо, потому что диски очень медленные. Одна из важных задач файловой системы - отслеживать какой файл относится к какому блоку.
___
Минимальная адресуемая область — сектор, минимум 512 байт, сейчас чаще 4096 байт. Это **физическая** единица.В блоке может быть несколько секторов, которые передаются как одна **логическая** единица. В первом случае адрес задается номером головки, дорожки и сектора, а во втором адрес логический, обработкой и занимается контроллер HDD, скорость передачи при этом вроде будет выше.

#### Contigious Allocation
Непрерывная аллокация. Каждому файлу какое-то непрерывное количество блоков. Возникают те же проблемы, что и со страницами в VM - внутренняя фрагментация.  На рисунке как это все выглядит.
![[Pasted image 20260126192040.png]]
У такого подхода есть несколько плюсов - 1) Легко искать файл - просто знаем начальный блок файла, и все блоки файла. 2) Производительность - весь файл может быть прочитан одной операцией.
Однако есть серьезный минус- удаленные файлы оставляют дырки в памяти, такая проблема уже была с страницами в виртуальной памяти, когда виртуальной памяти не хватало(при виртуальной памяти размером 128ТБ проблема недостатка мест в дырке как-то отпадает).   Если диск постоянно в работе - мы не можем его скомпактизировать - это очень долго. Тогда надо использовать дырки - но тогда надо хранить список дырок. Но тогда мы должны изначально знать сколько данных запишем на диск - это неприемлемо, например, для видео.
#### Linked-list аллокация
Будем хранит файлы, как связный список блоков, как на картинке. Каждый блок помимо данных содержит указатель на следующий блок в памяти. При таком подходе решается проблема внешней фрагментации - каждая часть диска может быть использована.

![[Pasted image 20260126183217.png]]
Тем не менее, такой подход очень медленный - чтобы прочитать последний блок, нужно прочитать n - 1 блок до этого. 
#### Linked-list Allocation Using a Table in Memory
#LinkedListAllocation
Создадим в памяти таблицу со всеми блоками диска. Запоминаем начало файла, допустим блок 4. В ячейке 4 таблицы, будет лежать номер следующего блока файла. Цепь заканчивается не валидным числом.  Такая таблица в системе называется **FAT- (File Allocation Table)**. Чем отличается от обычного linked листа - тем, что не надо именно **читать** предыдущие блоки, чтобы получить последний. 
![[Pasted image 20260126184559.png]]
Главный минус такого подхода - таблицу надо хранить в памяти. Она достаточно большая - это непрактично. Тем не менее FAT-based системы часто используются на картах памяти в цифровых камерах, плеерах, и в других embedded системах.

#### I-Nodes
#inode
Каждому файлу присваивается структура данных, которая называется **i-node(index node)**. Она содержит в себе атрибуты и адреса дисков блоков файла. I-Node находится в RAM только, когда файл открыт. В этом главное отличие - размер массива I-Node зависит не от размера диска, а от предельного количества открытых файлов. 
Есть одна проблема - если для файла в i-node выделено фиксированное количество адресов, то что делать, когда файл превосходит его. Одно из решений - последний адрес не на блок с данными, а на блок содержащий другие адреса.
