#### FS Backups
Чтобы не терять данные при, например, поломке диска, нужно делать бэкапы. Пользователи редко делают бэкапы, но компании делают это постоянно.
Бэкапы решают 2 проблемы.
1) Восстановление при поломке оборудования.
2)  Устранение пользовательских ошибок. Часто юзеры удаляют файлы, которые им потом будут нужны. Для этого на винде есть корзина.

Есть несколько вопросов:
1) всю ли ФС сохранять(например бинарники не надо, временные файлы - короче говоря не всю ФС надо сохранять). 
2) Также оптимально раз в месяц или неделю бэкапить все файлы, а каждый день делать дамп измененных файлов. Это называется **incremental dumps**. Тогда усложняется восстановление. Мы не можем просто делать снимок раз в условно неделю, потому что промежуточные файлы будут теряться + нет возможности анализа дампов, например на поиск вируса.  
3)  Можно сжимать файлы при записи на бэкап хранилище. Но у алгоритмов сжатия есть проблема - один поврежденный байт на диске, и мы теряем возможность разжатия файла - теряем весь бэкап,
4)  Нельзя делать бэкапы на активной системе, потому что файлы, директории постоянно меняются и удаляются. Есть решение - **снимки**. За доли секунды копируются ключевые структуры ФС - супер блоки, иноды, битмапы свободных блоков. Далее при изменении какого-то файла создается копия для бэкапа, и измененный файл. Снимки делаются на одном диске - если на другой то все будет очень долго работать. При этом раз в неделю можно делать бэкап на другой диск.
5) Проблемы безопасности - бэкапы надо защищать

Диски дампят 2 разными способами
1) Физический дамп. Начинает на блоке 0 диска записывать все блоки на другой диск по порядку. Есть проблемы. Нет смысла копировать пустые блоки, при этом если не копировать их, то нужно как-то хранить реальные адреса занятых блоков. Та же проблема с нерабочими блоками - ОС часто делает файл, состоящий только из битых блоков, чтобы они никогда не оказались в списке свободных блоков. Также часто эту проблему решает сам контроллер диска просто помечает блоки как нерабочие и вместо них использует рабочие из резерва. Короче говоря, если при бэкапе мы будем читать нерабочие блоки это приведет к ошибке бэкапа. Также нельзя делать инкрементированные дампы.
2) **Логический дамп**. Он начинается в какой-то специальной папке и рекурсивно дампит все файлы и директории, которые были изменены с последнего бэкапа. Таким образом диск дампа получает набор идентифицированных файлов и директорий - позволяет сохранять конкретный файл без проблем.

Восстановление ФС
На диске создается пустая ФС. Восстанавливается самый недавний дамп - восстанавливаются сначала директории, затем файлы. И так делаем для многих инкрементальных дампов, пока не получим ту версию, которая нам нужна. Проблемы возникают со списком свободных блоков - но его легко восстановить, и с ссылками - файлы надо дампить только 1 раз. Также не надо сохранять файлы, которые не являются файлами, например файлы, которые являются интерфейсами на ядро ОС.
Иногда ОС нужно создавать так называемые разряженные файлы
```c
struct user {
    int id;
    char name[100];
};

// Прямой доступ по индексу:
struct user* get_user(int user_id) {
    off_t offset = user_id * sizeof(struct user);
    lseek(fd, offset, SEEK_SET);
    read(fd, &user, sizeof(struct user));
    return &user;
}
```
Если для этой программки мы запишем 1000 пользователя, то 999 до него чем-то надо зафиллить. Здесь работают **sparse files**. На диске не хранятся данные - туда можно что то записать. Очевидно пустые нули мы не хотим бэкапить.
