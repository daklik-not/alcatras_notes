 #### Fundamental concepts  
Благодаря VFS Linux поддерживает множество FS. Linux может работать с FS как с модулями. Условно есть 2 раздела NTFS и FAT32. FAT32 находится в модуле, а NTFS в ядре. Тогда при обращении к FAT32 разделу модуль загрузится в ядро(и по идее там и останется)  
Размер имени файла ограничен 255 символами  
Файлы выглядят как name.extension  
Файлы хранятся в директориях. Директории тоже представлены как файлы.  
Есть несколько основных типов файлов:

Пользовательские директории  
Есть абсолютный путь и относительный (очев)  
Чтобы 2 пользователя имели доступ к 1 и тому же файлу используется **_link_**.(ДОБАВИТЬ ССЫЛКУ НА LINK В FS главе)  
Linux также поддерживает character special files и block special files.  
Открытие и чтение файла /dev/tty читает с клавиатуры. dev/lp пишет на принтер, dev/hdl позволяет читать напрямую из секторов диска(используется для программами, которые игнорируют FS, например recovery программы).  
Когда много дисков нужно ими управлять. Есть Windows подход - каждое диск образует свою собственную файловую систему, на которую без проблем можно установить драйвер. Тогда при обращении с 1 диска на другой нужно явно указывать диск. В Linux используется единая ФС, благодаря монтированию. При этом FS устройств сохраняются(условно если корневая FAT32, то NTFS не превратится в FAT32).  
Linux FS поддерживает **_locking_**. Если 2 процесса пытаются писать в файл происходит гонка.  
POSIX обеспечивает механизм блокировки файлов на уровне байтов. Механизм блокировки требует, чтобы тот кто обращается к файлу указывал файл, начальный и конечный байт, которые будут заблокированы. Если операция удается, система создает вхождение в таблицу, говоря что байты в запросе заблокированы  
Есть **shared lock** - сразу много файлов делят часть файла. Когда shared lock, другой процесс может также поставить его, но не exclusive. **_Exclusive lock_** - строго 1 процесс блокирует часть файла. При размещении блокировки, если lock нельзя сделать процесс может заблокироваться(то он просто ждет пока уже существующий lock уберут), или продолжить(получить успешный/неуспешный lock) и потом ждет если неуспешный

Очевидно, что shared lock, используется для чтения, а exclusive для записи.  
File-System Calls in Linux  
**_File System Calls_**  
![[Cache/Pasted image 20260522220738.png]]
Для создания файла используется:`  

```c
fd = creat("abc", mode) // создает и открывает
fd = open(file, how) // открытие(может вместе с созданием) для записи, чтения
```

Дескриптор файла всегда возвращается, как минимальный неиспользуемый дескриптор. У каждой программы первые 3 дескриптора занимаются stdin, stdout, stderr. Можно перенаправлять поток ввода в вывода, например.  
 ```c
n = read(fd, buffer, nbytes). //запись чтение
n = write(fd, buffer, nbytes)
lseek(fd, offset, whence) // перемещение указателя(не вызывает дисковую операцию)
 ```
  
Мы можем попросить у ОС какую-то статистику про файл.  
```c
s = stat(name, &buf)
```

Для создание пайлайнов используются **pipe syscall**. Они создают псевдофайл, который буферизирует данные и возвращают файловые дескрипторы для чтения и записи(канал односторонний если то)  
Этот вызов используется для блокирования  
```c
s = fcntl(fd, cmd) 
```

#### Implementation of Linux FS  
VFS прячет от высоко-уровневых процессов разницу между различными файловыми системами. Все Linux системы поддерживают множественное разделение дисков.  
***The Linux VFS***
*VFS* определят набор базовых абстракций файловой системы и операций над ними.
Вызовы системных вызовов, описанных в предыдущем разделе, обращаются к структурам данных VFS, определяют конкретную файловую систему, к которой принадлежит запрашиваемый файл, и через указатели на функции, хранящиеся в структурах данных VFS, вызывают соответствующую операцию в указанной файловой системе
В RAM находится всегда VFS в которую код ФС передает данные с диска
![[Cache/Pasted image 20260526142409.png]]
Есть 4 главные структуры
1. ***superblock*** - критическая информация для работы с ФС, например, таблица методов, которые выполняет конкретная ФС.
2. **inodes** - содержат описание каждого файла. Подробнее в ((Добавить ссылку на иноды в 4 чаптере)) #v-inode
3. **dentry** - директория, компонент пути, нужный для разрешения путей. Директории кэшируются в ***dentry_cache***. Кэш одинаковый для разных процессов PS: точнее dentry создает для каждого элемента пути, включая сам файл, жесткие ссылки, сим-линки и так далее.
4. ***file*** - структура данных, которая представляет файл, создается при open(). Системные вызовы де-факто вызываются на нее.
![[Cache/Pasted image 20260526143057.png]]
Каждая из структур содержит **operations** поле, которые указатели на функции для ФС.
Из user-space напрямую содержимое никак нельзя посмотреть.


***The Linux ext2 File System***

![[Cache/Pasted image 20260526143115.png]]
Весь раздел содержал ФС. Блок 0 нужен для bootingа.  Далее все память разбита на блоки. Каждый блок состоит из:
1. *superblock*. это не тот который в VFS. VFS суперблок хранится в памяти, этот хранится в файле на диске. Он содержит информацию о числе инодов, блоков, начале ССБ(нет по идее), где начинается таблица инодов, магическое число(уникальный идентификатор для ФС), версия ФС, размер блока, размеры структур.
2. *group descriptor*. Для своей группы хранит положение битовых карт, число свободных блоков и инодов, число директорий в группе. Вообще блоки нужны, чтобы равномерно распределять данные по диску и чтобы файл и его инод находились относительно близко.
3. *two bitmaps* по одной для блока и для инода.
4. *inodes*. сами иноды. $stat$ просто берет информацию с инода
5. данные.

Ext2 старается, чтобы обычные файлы находились в той же группе, что и родительские директории, и данные файлов в том же группе блоков что и искомый инод файла.
Когда новые блоки файлов выделяются, ext2 также преаллоцирует 8 дополнительных блоков для этого файла, чтобы уменьшить фрагментацию.

***The Linux Ext4 FS***
В ext3 была добавлена журналируемая FS. Ext4 также журналируема.  Почитать про журналируемые ФС можно здесь - #journaling_fs В Linux журнал представлен, как циклический буфер и сохраняются не в самой ext4 файловой системе, используется ***JBD(Journaling Block Device)*** для read/write. Важно добавить, что циклический буфер реализован на физическом уровне - то есть это непрерывные блоки на самом диске, а не абстрактно в ВАП например. 
Есть 3 структуры:
1. log record. Маленькая низкоуровневая операция, в границах одного блока. 
2. atomic operation handle. log record собираются в атомарные операции, то есть, например, системный вызов write().
3. transaction. чтобы не записывать на диск каждую атомарную операцию по отдельности все группируется в  транзакции.

Ключевая модификация - ***extents***(области).  Extents представляют из себя СД, которая хранит длительные непрерывные блоки. Условно, зачем храниться для 1GB непрерывного файла 1/1024 адресов для каждого блока, если можно работать с этой непрерывной областью как с 1 блоком.

***The /proc FS***
Для каждого процесса создается директория в /proc. Ее название это PID. Там файлы, которые содержат информацию о процессе. Этих файлов нет на диске, они только в RAM. Если зайти в папку **task** процесса, там будет информация по потокам этого процесса.


#### NFS: The Network File System
***NFS3***
Чтобы клиент с сервером могли нормально общаться интерфейс между ними должен быть строго определен. Есть несколько протоколов
1. Обрабатывает монтирование. Клиент может послать запрос на сервер, который, если разрешит, может вернуть ***file handle***, который содержит тип ФС, диск, номер инода, информация по безопасности. Далее для операций используется *file handle*. Таким образом файл смонтирован. При запуске Linux запускает /etc/rc скрипт перед тем как стать многопользовательской - добавляя туда нужные команды можно автоматически монтировать. Также можно использовать ***automonting*** - ассоциируем с локальной директорией удаленную. При открытие файла автоматически делается RPC(по нему есть заметка кстати со описанием сетевого протокола - #rpc). Автомонтирование чаще всего используется для Read-Only файлов, поскольку с сервером нет никакой синхронизации
```
/shared/bin  -ro  server1:/usr/bin  server2:/usr/bin  server3:/usr/bin
```
2. Получение доступа к файлам - чтение, запись. Поддерживается большинство системных вызовов, кроме open(), close(). Вместо open() делается lookup() который возвращает *file handle*. read делается по нему. Файл, который открыт клиентом не считается открытым на сервере(**stateless server**).

Для увеличения производительности используется кэширование. Сервер кэширует, чтобы избежать запросов к диску. Клиент кэширует в разных кэшах иноды и данные файлов.
Чтобы обеспечить когерентность этих кэшей, NFS для каждого вхождения реализует таймер(по истечению игнорируется). Когда файл открывается серверу посылается запрос, когда последний раз файл был модифицирован. Также каждые 30 секунд модифицированные страницы посылаются на сервер.
