***Text***
У каждого Linux процесса свое адресное пространство, которое состоит из text(машинные инструкции программы, read-only), data(константы), и стека. Когда у 2 программ одинаковый текст используются *shared text segmetns*, как на картинке. Дата и стек никогда не делятся.
***Data***
Data состоит из инициализированных данных и BSS.
За text сегментов следуют инициализированные данные. После инициализированных идет BSS. Бинарный файл состоит только из Data+Program text. При этом при запуске программы система выделит в ОЗУ память под эти неинициализированные данные. Короче говоря это просто экономия места на диске .Мы храним на диске только сколько памяти  нужно выделить под не инициализируемые переменные в заголовке например, а ОС сама уже при запуске выделяет память в BSS сегменте под память. Чтобы не выделять кучу пустых страниц Linux выделяет 1 **zero** page для процесса. При запуске неинициализированные данные указывают на эту страницу. Когда процесс пытается что-то записать CoW аллоцирует реальную страницу для нужной памяти. Потом все остальные обращения мапятся на эту страницу, или если BSS больше размера страницы, то потом еще одна создается.
Data segment может меняться в размерах. Системный вызов **brk** позволяет программе устанавливать размер своего data segment. C процедура **malloc** используется для аллокации памяти. Диапазон динамически выделенных адресов в процессе обычно называется **кучей(heap)**. Куча начинается сразу после BSS и обычно растет вверх. 
***Stack***
Стек начинается на вершине ВАП и растет вниз. Программы явно не управляют размером стека. Изначально стек содержит переменные окружения(PATH=) и argv.  В стеке находятся сами строки и указатели на них.

#### Memory-Allocation Mechanisms
Аллокатор страниц в Linux называется ***buddy algorithm***.
Изначально память состоит из единого непрерывного куска.  Когда приходит запрос, то он округляется сначала до степени 2 и далее непрерывный кусок делится на 2, пока не появится чанк с нужным количеством страниц.
![[Pasted image 20260517194915.png]]
Далее приходит еще запрос для 8 страниц. Делается как на картинке
![[Pasted image 20260517195139.png]]
Потом несколько страниц релизится, и непрерывные снова объединяются в большие, как на картинке

Все это управляется с помощью массива, где $i$ элемент это головка двусвязного списка с  блоками размера $2^i$. Но такой массив же уже есть: buddy page allocator работает обращаясь к zone descriptor для получения списка свободных блоков.

Такой алгоритм приводит к внутренней фрагментации. Чтобы решить эту проблему, для некоторых случаев Linux использует ***slab allocator***. 
Он принимает чанк от buddy(допусти 128КБ чанк, где 65КБ реальных данных). Slab нарежет полученный чанк на маленькие части. Причем slab работает как кэш, то есть он не выкидывается сразу, а остается там. И если такой же объект понадобиться, то его сразу выделят(что в конкретном примере маловероятно, поскольку это рандомно память просто). Более вероятно такое в следующем примере: ядро часто создает и разрушает объекты определенного типа(task_struct например), и чтобы каждый раз не выделять фрагментированную страницу, такие объекты кидаются в slab.

#### Paging in Linux
Swapping система в Linux работает с точностью до страниц и совмещена с ***page reclaiming algo***.
*Paging* частично реализуется специальным процессом **page daemon**. Этот демон - процесс 2 - ***kswapd***. Этот демон работает периодически, просыпается, очищает страницы, идет дальше спать(В доках Linux написано, что только когда нижняя вотермарка достигается)

В Linux используется *полностью* demand система и отсутствует понятие рабочего набора как такового. 
Файлы и код выгружаются на свои оригиналы(файл на диске и бинарник). Все остальное выгружается в *swap area*. Чаще всего под swap area подразумевается специальный раздел на диске. #swap_area  Используется битовая карта, чтобы понимать, какие страницы свободные. Далее, когда надо выгрузить анонимную страницу, ядро выбирает swap с наивысшим приоритетом(оказывается свопов может быть несколько), в которой еще есть свободные слоты. Далее таблица страниц обновляется, в нее записывается (номер устройства swap + номер страницы в нем).


#### Page Replacement Algo
Linux старается сохранить несколько страниц свободными. Этот пул пополняется с помощью ***PFRA(Pafe Frame Reclaiming Algorithm)***. Linux различает между 4 типами страниц
1. *unreclaimable* не могут быть выгружены, например стек ядра ОС.
2. *swappable* должны быть выгружены в swap до того как их снова восстановят из диска. Грубо говоря, страницы, которые не имеют постоянного бэкинга на диске.
3. *syncable* - должны быть записаны на диск, как только у них появляется Dirty бит. Например файлы.
4. *discardable* - страницы, которые можно просто выбросить. Например страницы выделенные под временные буферы.

Во время запуска init запускает **kswapd** для каждой ноды памяти(вспоминаем NUMA архитектуры).  Далее он сравнивает текущее использование памяти для каждой зоны с специальными вотермарками  Вотермарки показывают уровни памяти. То есть kswapd всегда старается поддерживать количество страниц для процесса как минимум на уровне вотермарки high. За 1 заход можно выгрузить только меньше 32 страниц.

Каждый раз PFRA сначала пытается выгрузить 4 тип страниц - помещает их в zone_freelist. Далее пытается искать 2,3 тип на который давно не ссылались, используя clock-like алгоритм. Далее разделенные страницы, которые мало кто использует. С ними проблема в том, что нужно обновлять все таблицы страниц всех процессов. Это очевидно очень медленно, но Linux с помощью деревьев позволяет быстро искать всех пользователей этой страницы(вроде через struct page). Далее обычные пользовательские страницы. Отношение обычных страниц к страницам с backing store определяется как параметр алгоритма. Далее невалидные страницы, залоченные, используемые DMA просто игнорируются

PFRA использует clock-like алгоритм, чтобы выбирать страницы на выгрузку для определенной категории. Для этого  алгоритм содержит цикл, который бегает по каждому active_list и inactive_list списку зоны(то есть есть список для страниц, который часто используются и есть список которые не очень часто используются). Как параметр передается, сколько страниц должен проверить алгоритм
