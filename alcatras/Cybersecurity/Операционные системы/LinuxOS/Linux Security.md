
***Fundamental concepts***
У каждого пользователя свой **UID***(0-65535). У файлов и процессов помечается пользователь. Пользователи могут быть сгруппированы - **GID**.
![[Pasted image 20260526233021.png]]
У каждого процесса есть GID и UID. Таким образом, тот кто создает файл, указывает какие к нему есть права у него, участников его группы, остальных
![[Pasted image 20260526233443.png]]
Из интересного: 6-ой тип. Его можно использовать для *dummy* файлов. Это файлы, которые просто имитируют обычный файл. Можно использовать его для разных целей. Например можно забить ФС и посмотреть как она будет вести себя при больших нагрузках. Также можно например, блокироваться на файле(то есть процесс в конце работы должен удалить файл, а в начале создать).

UID=0 - **root**. Процессы с 0 UID также могут делать небольшое число защищенных системных вызовов, например reboot(перезагрузка). Имеется в виду, что да, сделать системный вызов может кто угодно, но получить его результат только root.

***SETUID***
10 бит - ***SETUID*** бит. 
Как это работает. Есть исполняемый файл - обычная программа, например, *passwd* для смены пароля, она принадлежит UID = 0. На нее устанавливается бит SETUID.  В коде программы есть read() к файлу, у которого UID тоже 0. 
Теперь запускается пользовательский процесс. Он может выполнить программу, но не может открыть файл. Тогда процесс через *fork* может запустить программу. Процесс, запущенный через *fork*, получит не обычный UID родителя, а EUID программы, поскольку в программе установлен бит SETUID. 
Таким образом, искомый пользовательский процесс, может совершать над файлом только те действия, которые заданы в программе с битом SETUID.

***Implementation of Security In Linux***
Когда пользователь логинится, запускается login программа(SETUID root), которая запрашивает пароль и логин. Пароль хэшируется. Если авторизация прошла, то ОС смотрит предпочитаемый шелл в /etc/passwd.
![[Pasted image 20260527010655.png]]
Далее ей с помощью setuid(), setgid() выдаются соответствующие права. Далее открываются потоки(0,1,2) и связываются с устройствами.

Когда процесс пытается открыть файл, система проверяет *protection* биты. Она сравнивает пользовательские с тем, которые в VFS иноде файла. Если protection мод изменен после того, как у процесса уже есть к нему доступ, то ничего не поменяется для процесса.
