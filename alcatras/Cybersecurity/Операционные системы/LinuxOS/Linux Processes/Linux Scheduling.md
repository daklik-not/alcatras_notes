### Scheduling in Linux
Linux потоки это kernel-level потоки поэтому планирование осуществляется по потокам, а не по процессам

В контексте планирования потоки разделяются на 4 типа:

1. Real-time FIFO(высший приоритет, вытесняются только потоками с еще большим(тоже real-time FIFO)). Представлены приоритетами от 0 до 99
2. Real-time round-robin(вытесняются часами - квант времени)
3. Sporadic(неожиданные, асинхронные события - нужны чтобы путем ограничения не подвергать опасности real-time потоки)
4. Timesharing - стандартный timesharing

  Время тика можно конфигурировать(герцы). На новых системах используются  **high-resolution-timers**. Они очень точные

Linux ассоциирует *nice* значение с каждым потоком. По умолчанию оно 0(-20:19).  Только системный администратор может попросить значения лучше, чем нормальный сервис - а именно (-20, - 1). Фактически *nice* является некой пользовательской подсказкой для планировщика

#### O(1) scheduler

Выбор задачи, или ее постановка в очередь выполнялись за O(1).

*runqueue* организована через 2 массива - *active*, *expired*.

В каждом из массивов было 140 очередей, где в $i$ очереди находились процессы с $i$ приоритетом.

Планировщик выбирал задачу из высокоприоритетного списка в активном массиве. Если ее квантум истекал она перемещалась в *expired* массив(вероятно с более низким приоритетом). При блокировке из *expire* она снова помещается в active, ее квантум уменьшается на уже использованное время. Когда квантум истекает задача помещается в expired массив. Когда в *active* больше нет задач, делается *swap(active_pointer,expired_pointer*. Разным приоритетам разный квантум. IO-bound процессы получают динамическое повышение приоритета, чтобы быстрее освобождать процессорное время для CPU-bound.

Есть динамический приоритет, а есть статический приоритет. Динамический постоянно пересчитывается -  он может давать +-5 к приоритеты(в этом планировщике). Для определения использовалась переменная $sleep\_avg$. Когда процесс спит, его sleep_avg увеличивается, когда процесс работает оно уменьшается.

Ну короче он плохо работал на мультипроцессорных системах, поэтому придумали *CFC*

#### CFS - Completely Fair Schedule

Дефолтный планировщик не для real-time задач.

В качестве *runqueue* использовалось красно-черное дерево. Задачи упорядочивались в дереве, основываясь на количестве времени запущенном на CPU - **vruntime**. Точность в наносекундах.

![[Pasted image 20260515234022.png]]

Это можно посмотреть в /proc/PID/vruntime или /proc/PID/task/TID/sched

*Алгоритм планирования*

CFS всегда запускал задачу с самым маленьким количеством CPU времени(самая левая вершина дерева). Периодически *CFS* увеличивается *vruntime*, выполняется перестройка дерева(если нужна, и если нужна то запускается новая задача, с минимальным vruntime).

*nice* используется для определения частоты передачи информации о vruntime(ну типо как часто дерево перестраивается).

Ну и очевидно, что работает оно за $O(\log n)$(вставка)

*runqueue* структура копируется для каждого процессора. Однако CFS старается выполнять задачу на 1 и то же процессоре. С помощью системных вызовов можно задать на каких ядрах будет поток выполняться: $sched\_setaffinity()$. Также планировщик старается распределит нагрузку между всеми процессорами.

CFS работает только с активными процессами(незаблокированными).  Заблокированные потоки помещаются  в **waitqueue**. Она ассоциируется с каждым событием, которого ждет задача. То есть условно для 2 потоков, которые блокируются на  1 файле, только 1 waitqueue. Также в waitqueue есть спинлок, который синхрониизует доступ к очереди между несколькими потоками.
