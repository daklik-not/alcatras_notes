#### Locking Pages in Memory
Пусть процесс вызывает системный вызов на чтение из файла или устройства в буфер внутри своего адресного пространства. Пока процесс ждет завершения IO, он приостанавливается и другой процесс запускается. Другой процесс получает page fault.
Если используется глобальный paging существует небольшой шанс, что страница, на которую DMA загружает данные будет заменена. В таком случае часть данных запишется первую страницу, часть на новую. 
Для решения можно закреплять - **pinning**  - страницы, содержащие IO операции в памяти. Так же можно записывать все IO в буфер ядра, и затем копировать его в пользовательский буфер - но это двойное копирование - замедляет процесс.

#### Backing store
#swap_area
Самый простой алгоритм выделения места на энергонезависимом хранилище (backing store) — это иметь специальную область подкачки (swap area), отдельную от файловой системы. В этой области нет структур файловой системы, то есть не требуется преобразовывать смещение в файле в номера блоков на диске. Говоря грубо, в swap area стремятся к тому, чтобы одному блоку на диске соответствовала одна страница памяти, и отсутствовали сложные дополнительные структуры, характерные для файловых систем.
Обычно при запуске системы swap area пуста. Простейший алгоритм выделения памяти в ней выглядит так: при запуске процесса для него сразу выделяется место в swap area, равное полному размеру его адресного пространства. (сейчас все on-deman) При этом область подкачки увеличивается, а свободное место на разделе диска уменьшается. Управление этой областью ведётся с помощью чанков (блоков), размер которых кратен размеру страницы.
Каждый процесс будет выгружаться на диск в ту часть swap area, где заранее сохранён его снимок (образ адресного пространства). Информация о расположении этого снимка хранится в PCB процесса. Чтобы вычислить адрес для записи или чтения конкретной страницы, достаточно прибавить смещение этой страницы в виртуальном адресном пространстве к начальному адресу swap area процесса.
Существует два подхода к инициализации: можно сначала загрузить процесс в оперативную память (RAM), а затем выгружать страницы на диск по мере необходимости (по запросу, on demand). Альтернативно, можно сразу загрузить весь образ процесса на диск, а затем подгружать страницы оттуда. У второго подхода есть проблема — процессы могут расти (например, расширяться стек или куча). Поэтому лучше хранить отдельные области подкачки для разных сегментов данных процесса (например, отдельно для кода, данных и стека).
В целом, более эффективно выделять место в backing store только в тот момент, когда страница реально выгружается на диск, и освобождать это место, когда процесс завершается или страница явно освобождается. В таком случае необходимо понимать, какой виртуальной странице какое место на диске соответствует. Для этого требуется таблица, которая для каждой страницы будет хранить информацию о её расположении на диске.
