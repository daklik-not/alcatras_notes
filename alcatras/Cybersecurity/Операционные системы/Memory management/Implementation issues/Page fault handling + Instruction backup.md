#### Page fault handling
Подробное описание того, что происходит при page faulte
1.  Аппаратное обеспечение посылает аппаратное прерывания ядру, сохраняя program counter и program status word на стеке ядра процесса. На большинстве машин, на регистрах процессора сохраняется некоторая информация о состоянии текущей инструкции.
2. Ассемблер-код обработчика прерываний немедленно сохраняет полное состояние всех регистров общего назначения и других критических регистров процесса в предварительно выделенную область ядерного стека прерванного процесса. 
3. ОС пытается выяснить, по какому виртуальному адресу обратился процесс, когда произошел page fault. Часто один из регистров аппаратного обеспечения содержит эту информацию. Если нет ОС должна сфетчить инструкцию, используя программный счетчик и разобрать ее.
4. Далее система проверяет, валидный ли адрес, и есть ли у процесса доступ к страничному кадру. Если нет, процессу посылается сигнал. Если да, система проверяет, есть ли свободные страничные кадры, если нет, то запускается алгоритм замены страниц(обычно он работает в фоне, и на момент page fault уже нашел нужную страницу).
5.  Если выбранный страничный кадр dirty, то страница планируется на перенос в не энергозависимое хранилище - происходит context switch, блокируя процесс, до того как перенос не завершится (это при блокирующем IO).  
6. Как только страничный кадр записан на диск, ОС ищет адрес новой страницы в swap area и запускает операцию для переноса его в RAM. Процесс все еще заблокирован.
7. Когда диск или SSD посылают прерывание о том, что новая страница готова, таблица страниц обновляется, чтобы отображать ее позицию и present bit = 1.
8. ОС вновь запускает инструкцию, которая вызвала page fault, обновляя программный счетчик.
9.  Процесс планируется, управление возвращается из **page fault handler** - кода ОС, написанного на C к ISR.
10. Рутина перезагружает регистры и другую информацию, и возвращается в пользовательское пространство
#### Instruction backup - из 8 пункта
ОС не может просто взять и запустить инструкцию сначала. Чтобы перезапустить инструкцию, ОС должна определить где был первый байт инструкции. Значение программного счетчика в момент прерывания зависит от того, какой из операндов вызвал page fault - MOVE, первый или второй.
К тому же, некоторые процессоры автоинкрементируют/декрементируют адреса. Это полезно, например при работе с массивом - вместо 2 инструкция чтения и сдвига адреса - одна инструкция.

На некоторых процессорах, инженеры CPU предоставили решение. В процессоре есть один внутренний регистр, куда копируется значение программного счетчика перед запуском инструкции. Также у них есть второй регистр, который содержит информацию о инкрементации адресов. Это решает проблему.
Тем не менее, если если такой опции нет, ОС должна сама выяснять, где произошла проблема, что достаточно сложно.
