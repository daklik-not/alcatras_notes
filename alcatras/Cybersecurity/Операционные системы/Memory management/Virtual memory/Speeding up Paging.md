### Speeding up paging
Для хорошей реализации paging должно выполняться 2 условия
1. Mapping - сопоставление должно быть быстрым. Все инструкции приходят из памяти и более того ссылаются на память. Обращение к таблице страниц не должно занимать большую часть времени выполнения инструкции. 
    [[Speed Speed UP - (TLB)]]
2.  Даже если виртуальное адресное пространство большое - таблица страниц не должна быть большой. Например, когда используютя 48-битные адреса, различное количество адресов - $2^{48}$ - порядка 64 миллиардов страниц, что весит несколько гигабайт.  А в классической реализации у каждого процесса должна быть своя таблица страниц [[Memory decrease - (Multilevel~Inverted page tables)]]

Самый простая архитектура - иметь одну таблицу страниц, состоящую из быстрых регистров, с одним вхождением на каждую виртуальную страницу, индексируемую по виртуальному номеру страницы. Когда процесс запускается, операционная система загружает регистры вместе с таблицей страниц процесса взятой из RAM. Плюс такого подхода в том, что не нужно ссылаться на память(Насколько я понимаю имеется в виду то, что если таблица реализована в RAM, а не на регистрах, то MMU просто не будет ссылаться на оперативную память при преобразовании адресов - все лежит на аппаратныхх регистрах. С другой стороны я не понимаю, насколько дорого это будет если под регистрами впринципе понимается небольшая сверхбыстрая память - а здесь надо хранить гигабайты памяти). Также загружать всю таблицу страниц при каждой смене контексте дорого.

С другой стороны таблица страниц может быть полностью в главной памяти. Тогда нужен один регистр, который указывает на таблицу страниц. У каждого процесса должна быть своя таблица страниц - регистр отвечает за указатель таблицы внутри процесса.  Проблема такого подхода в том, что память в RAM достаточно медленная относительно регистра - нужны memory reference - это сильно замедляет работу.
