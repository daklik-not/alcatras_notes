### Page Tables for Large Memories
TLB ускоряет работу сопоставления но при этом никак не решает проблему того, что таблица страниц адресов может быть очень большой - занимать много места в памяти.
#multilevel_page_tables
#### Multilevel Page Tables
Секрет в том, чтобы не хранить все таблицы в памяти в одно и то же время. Допустим возьмем 32битный адрес. Разобьем адрес, как показано на картинке - 10 бит на PT1, 10 на PT2, и 12 на offset. `offset` — это смещение **байта инструкции внутри страницы**. PT1 будет отвечать за индекс в **top-level page table** или же **page directory**. По этому индексу будет находиться таблица страниц для определенного количества памяти, в моем случае 4MB. PT2 будет отвечать за индекс в таблице страниц - вхождение по этому индексу, это уже страничный кадр - реальный физический адрес. **Page directory** точно также будет хранить в себе  Presense биты. Если Presense bit равен 1, то все нормально, если нет - генерируется page fault - ОС выделяет память и генерирует таблицу страниц памяти для только что выделенной памяти. После этого все как обычно. TLB кэширует только конечные трансляции из виртуального адреса в реальный. Если нет MMU делает page table walk через все эти уровни.

Почему это вообще работает? Как я понял это нужно для того, чтобы память для процесса выделялась лениво - то есть не сразу а по мере использования. В реальных системах будет расти стек и куча. Таким образом система будет хранить в RAM минимальное количество адресов. Грубо говоря, это просто еще одно разбиение памяти, такое же как и страницы памяти.
Что то похожее на таблицу, описанную выше использовалось на Intel 32битном 80386 процессоре, который мог адресовать 4ГБ памяти. Через 10 лет Penrium Pro перешел к 3уровневой организации - **page directory pointer table**. В нем было 4 входа в page directory pointer таблице, 512 в каждой page directory  и 512 в каждой page. Общее количество памяти по прежнему было 4 GB. Короче говоря оно так расширялось, потом появилось **page map level 4**. $2^9$× $2^9$ × $2^9$ × $2^9$× $2^12$= $2^{48}$ bytes - сейчас в адекватных системах используется что то подобное.

#### Inverted page Tables
В этой архитектура - одно вхождение на страничный кадр в RAM, а не одной вхождение на страницу виртуального адресного пространства. На самом деле 
в RAM хранится специальная таблица - IPT, которая по каждому индекс которой - физический кадр, а внутри лежит виртуальный адрес и pid. Все записывается при выделении памяти. У MMU есть пара n,v - номер процесса и виртуальный номер страницы соответственно. По ним генерируется хэш-функция, после чего по ней индексируем адрес в массиве.
