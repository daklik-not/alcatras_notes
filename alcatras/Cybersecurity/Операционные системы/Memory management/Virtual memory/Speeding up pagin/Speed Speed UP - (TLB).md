#### Translation Lookaside Buffers
Главная проблема в том, что таблица страниц находится в памяти. При прямом обращении к регистру инструкция обратится только 1 раз к памяти - чтобы сфетчить инструкцию. При подходе с виртуальными адресами добавится как минимум 1 доп обращение к памяти - обращение к таблице страниц. Это понижает производительность во много раз. Это проблема существует очень давно -  основное ее решение в том, что процессу реально часто нужен очень небольшой диапазон адресов - остальные используются крайне редко.
Каждый компьютер оснащался специальным устройством для сопоставления виртуальных адресов с реальными без использования таблицы страниц. Его назвали **TLB - Translation Lookaside Buffer** который использует **associative memory**. Он находится внутри MMU и состоит из небольшого количества вхождений, обычно меньше 256.(Deepseek пишет, что есть 2 типа TLB - L1 TLB - как раз таки примерно такого размера и L2 TLB - он уже от 512 до 2048 записей ) Каждое вхождение содержит информацию об одной странице.

Когда виртуальный адрес передается MMU для перевода, аппаратное обеспечение  сначала проверяет, есть ли номер виртуальной страницы в TLB, сравнивая все вхождения *параллельно*. Это возможность дает особенность архитектуры TLB. Если страница нашлась - она берется из прямо из TLB без использования таблицы страниц. Если страница защищена битом, генерируется *protection fault*.
Когда страница не в TLB, MMU определяет ошибку и ищет физический адрес в таблице страниц в оперативной памяти. Затем он убирает одну из записей в TLB и заменяет ее нужной страницей. Когда страница убирается из TLB, modified бит копируется обратно на таблицу страниц в памяти(Deepseek пишет, что он меняется аппаратно при первой записи на страницу)  Когда entry загружается в TLB все поля берутся из памяти.
Если ОС хочет изменить бит в entry, то она будет менять значения таблицы в памяти. Если страница в TLB, ОС должна заново загрузить entry в TLB, чтобы изменить биты

### Software TLB management
В некоторых архитектурах управление TLB и обработка TLB fault происходит полностью под управлением MMU. Операционная система работает только при подгрузке страниц с диска.
Однако так не на всех системах. Когда происходит TLB miss, то MMU просто генерирует прерывание для ОС. Система должна найти страницу, убрать entry из TLB, добавить новое и перезапустить прерванную инструкцию. И это все должно делаться быстро. TLB misses происходят значительно чаще чем page faults поскольку размер TLB памяти достаточно маленький. Такой подход помогает уменьшить размер MMU, что освобождает место для кэша.

**Soft misses** - страница не в TLB, но в памяти. Требует 10-20 машинных инструкций для обработки - 200-400 наносекунд - основная задержка обращение к рам
**Hard misses** - страница впринципе не в RAM.  Это занимает в миллион раз дольше чем soft miss.
Весь процесс называется **page-table walk**. Сначала проверяется TLB - потом память - потом диск.
Вообще различают несколько причин промахов.
**Minor page fault** - страница реально находится в памяти, но в виртуальном адресном пространстве другого процесса. Тогда страницу не надо подкачивать из памяти - просто нужно правильно сделать сопоставление. Типичные случаи для такого fault - разделяемая память, и CopyOnWrite при fork(). Они по разному обновляются но основная идея в том, что для диагностики они смотрят Present bit. Если он равен 1, то страница уже в памяти - то есть ее загрузил другой процесс. Тогда программа ищет ее в **page cache**. Если есть просто меняет PTE страницы. Если нет, то подгружает с диска страницу, но вроде как почти всегда эта страница будет в кэше. Для CPW немного другой механизм, там просто выделяется новая страница памяти, после того как ОС определила что это именно CPW
**Major page fault** - страницу надо подкачивать из памяти
**Segmentation fault** - программа обращается по неправильному адресу. Только в этом случае аппаратное обеспечение  или операционная система не могут починить возникшую проблему. Или нет прав.
