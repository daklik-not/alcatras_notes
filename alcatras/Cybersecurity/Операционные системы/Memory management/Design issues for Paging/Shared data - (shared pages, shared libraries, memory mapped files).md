#### Shared Pages
В больших мульти программируемых системах пользователи часто запускают одни и те же программы. Очевидно мы не хотим, чтобы одинаковые для процессов страницы были в памяти в двойном экземпляре.

Если в системе доступно разделение на адресные пространства для инструкция и для данных, то механизм прост. В таблице процессов для каждого процесса будем хранить указатель на общее для всех процессов код программы, и на свой data segment. Без разделения процессы могут разделять программы или библиотеки но механизм намного сложнее.
Для разделяемых страниц возникает проблема - когда один процесс выгружается из памяти - он выгрузит и общие страницы. Тогда нужен механизм, понимания общая страница или нет.
Бегать по таблицам страниц слишком дорого - нужны специальные структуры данных, чтобы понимать какие страницы разделяемые.

Разделять данные сложнее чем программу. Яркий пример такого разделения - fork(). При создании процесса дочерний процесс ссылается на те же страницы, что и родительский. Но при этом ОС устанавливает во все страницы READONLY бит. При первой записи сгенерируется программное прерывание - и система выделит новые страницы и новую таблицу страниц для дочернего процесса.

В общем случае для разделяемых страниц используется **reference count**. В структуре таблицы хранится счетчик ссылок, показывающий сколько виртуальных адресов на него ссылается.

#### Shared Libraries
В современных системах многие большие библиотеки используются многими процессами - например множество IO и графических библиотек. Очевидно мы не хотим для каждого процесса отдельно загружать с диска эту библиотеку.
Используется техника **shared libraries**, которая называется **DLLs or Dynamic Link Libraries**. 
Программа линкуется(объектные файлы сливаются в 1 большой исполняемый файл). Мы видим инструкцию, которая только объявлена в объектном файле. Пример printf и библиотека stdio.h. Когда линковщик понимает, что в объектном файле реализации функции нет, он начинает искать ее в библиотеке, где реализация хранится уже в виде бинарника. Такие функции называются **undefined externals**. То же самое относится к функциям, которые ждут другие функции. Когда линковщик заканчивает, выполняемый бинарник записывается на энергонезависимое хранилище. Функции, которые находятся в библиотеке, но не используются не загружаются. Каждый раз просто линковать функции из библиотеки в процесс невыгодно - сначала они занимают место в RAM - потом на диске.
Когда процесс линкуется с shared библиотекой, вместо того чтобы включать реальную функцию, линкер загружает маленькую заглушку, которая вызывает функцию во время работы программы. Короче с помощью заглушки линкер находит реальный адрес уже загруженной в RAM библиотеки. Главное - если одна программа уже загрузила в RAM библиотеку, другая программа не будет этого делать. Подгружается не вся библиотека - лениво подгружаются только нужные функции. Также ее страницы работают по тем же алгоритмам что и обычные - если страница часто не используется она будет выкинута из памяти.  Если библиотека обновится до новой версии, то не надо будет перекомпилировать файл - заглушка говорит просто искать адрес в памяти, а не подгружает функцию в бинарник.

У shared библиотек есть небольшая проблема. Библиотека не может быть релоцирована на лету. Допустим в библиотеке первая инструкция - jump 16. Он прыгнет на 16 адрес. Но по факту библиотека находится для каждого процесса в разных местам, а релоцировать мы ее не можем, поскольку процесс не может влиять на код библиотеки.
Решение этой проблемы - будет компилировать библиотеки в **position independent code**. То есть в таком коде нет инструкций - пойди на адрес 2. Вместо этого она работает сдвигами - сместить на 2 байта..
