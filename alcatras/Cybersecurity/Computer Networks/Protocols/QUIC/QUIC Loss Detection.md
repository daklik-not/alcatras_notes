#### QUIC Loss Detection

*Проверка и аутентификация*
На канальном уровне есть проверка на CRC. После нее идет UDP проверка.
Если и то и то прошли, то запускается AEAD проверка на уровне QUICK. 
Смысл AEAD в том, что создается *MAC* или тег аутентификации. Он вычисляется по заголовкам и по пейлоуду. То есть я не могу менять заголовки.  Интересно, что если MAC не проходит, то это просто считается за атаку, и соединение прерывается.
Что интересно -  **В TCP такой защиты нет**. Я могу свободно редактировать заголовки. 

ACK, PADDING,CONNECTION_CLOSE - not eliciting
*Разница в механизмах*
1. По одному QUIC соединению не может быть отправлено 2 пакета с одинаковым номером. Если пакет теряется, то его кадры перенаправляются в другом пакете.
2.  Опознавания значительно более подробные
3.  В 1 пакете могут быть совершенно разные кадры. Пока их не опознали, надо их буферизировать и пометить
4. Есть кадры, которые не надо опознавать - ACK, PADDING, CONNECTION_CLOSE.  Если пакет содержит хотя бы 1 кадр не из этих 3, его надо опознавать.

*Опознавания*
Есть 2 типа опознаваний - обычное  и опознавание, которое содержит информацию о ECN флагах. 
```
ACK Frame {
   Type (i) = 0x02..0x03,
   Largest Acknowledged (i), // наибольший номер опозн. пакета
   ACK Delay (i)
   ACK Range Count (i),
   First ACK Range (i),
   ACK Range (..) ...,
   [ECN Counts (..)],
}

ACK Range {
   Gap (i),
   ACK Range Length (i),
}
```

**ACK Delay (i)** -разница между временем получения с самым большим номером и передачей опознавания. Нужно для понимания задержки сервера.  Пример на картинке

В QUIC запрещено отправлять подтверждение на пакеты, которые полностью состоят из фреймов, которые не надо подтверждать(non-eliciting).  В обратном случае мы могли бы вызвать бесконечную цепочку подтверждений. Чтобы как-то получить данные, о том дошли ли опознавания, мы можем завернуть 1 ACK, в пакет с фреймами, которые требуют подтверждения(PING например), таким образом мы опознаем наш ACK.

QUIC не использует опознавания типа(1-10 пакет были доставлены) - **cumulative ack**, потому что пакеты перенаправляются с другим номером. Чтобы заполнять ACK range, QUIC использует специальные эвристики. Например QUIC посылает кадр опознавания несколько раз.

Если внимательно посмотреть, то можно заметить, что *packet_number* идут не по порядку.
Дело в том, что QUIC разбивает соединение на 3 части:
1. Обмен Initial
2. Обмен Handshake
3. Обмен 1-RTT
Для каждой фазы он создает *packet_number=0*

В QUIC есть поддержка ECN(Explicit Congestion Flags).  Ну короче перегруженные роутеры ставят метки в IP пакетах, которые QUIC может копировать к себе, и отправлять получателю
```
ECN Counts {
   ECT0 Count (i),
   ECT1 Count (i),
   ECN-CE Count (i),
}
```
