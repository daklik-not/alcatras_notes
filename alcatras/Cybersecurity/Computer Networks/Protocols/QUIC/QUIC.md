**QUIC address spoof protection***
Есть плохой клиент. Он отправляет Inital на мощный сервер, но с чужим IP. Сервер посылает по тому IP огромный пакет с криптографическими параметрами, крипто-алгоритмами. Таким образом происходит *reflective DoS атака*. 
У QUIC есть защита:
1. Initial пакет, отправляемый клиентом - большой. Таким образом нет такой большой разницы между тем, что отправляет плохой клиент и сервер хорошему клиенту(хотя она есть просто не так заметна)
2. Сервер может попробовать валидировать клиента, что тот может получить пакеты отправляемые сервером. Для этого он отправляет *token*.  ![[Pasted image 20260605154745.png]]
   Сам токен должен быть тяжело предсказуемый, например какой-то хэш. После этого клиент, если он настоящий, отправит еще одно сообщение Initial, но уже с токеном.
#### Identifying QUIC connections
Когда клиент посылает изначальный пакет, он указывает source *CID*, который уникально идентифицирует соединение на клиенте и удаленном CID(SCID и DCID). Далее сервер делает то же самое.
![[Pasted image 20260605154751.png]]
Во время передачи пакетов используется только DCID. Размер CID отлично от TCP может меняться.  Например, перед сервером может стоять *load balancer*, который будет распределять нагрузку между серверами. Тогда DCID сервера может состоять из уникального идентефикатора+идентификатора сервера, куда надо отправить пакет. 
Здесь клиент будет слать с (x,z), а сервер с (z,x)

 В сетях есть проблема, которая называется **protocol ossification**. Сетевые устройства подстраиваются под протокол, лишая его возможности развиваться. 

Чтобы не позволить сетевым устройствам легко распознавать QUIC трафик, QUICK шифрует 
все Initial пакеты, используя DCID со стороны клиента и сервера(каждый своим). Кроме зашифрованного пакета, хосты увидят сам незашифрованный DCID. С точки зрения безопасности в этом не очень много смысла, но помогает предотвращать **protocol ossification**. Код ниже:
```c
initial_salt = 0x38762cf7f55934b34d179ae6a4c80cadccbb7f0a
initial_secret = HKDF-Extract(initial_salt,
                        client_dst_connection_id)

client_initial_secret = HKDF-Expand-Label(initial_secret,
             "client in", "", Hash.length)
server_initial_secret = HKDF-Expand-Label(initial_secret,
                           "server in", "",Hash.length)
```

#### QUICK packet headers

QUIC использует заголовки пакетов с динамической длиной. Есть 2 формата заголовков.

***Long*** 
```
Long Header Packet {
  Header Form (1) = 1,                  /* high order bit of the first byte */
  Fixed Bit (1) = 1,                    /* second order bit of the first byte */
  Long Packet Type (2),                 /* third and fourth high order bits of the first byte */
  Type-Specific Bits (4),               /* low order four bits of the first byte */
  Version (32),                         /* 32 bits version number */
  Destination Connection ID Length (8), /* 8 bits */
  Destination Connection ID (0..160),   /* variable number from 0 up to 160 bits */
  Source Connection ID Length (8),
  Source Connection ID (0..160),
  Type-Specific Payload (..),           /* variable length */
}
```
Он используется для *Initial*, *Handshake*, *Retry* пакетов.
```
Initial Packet {
  Header Form (1) = 1,                   /* High order bit first byte */
  Fixed Bit (1) = 1,
  Long Packet Type (2) = 0,
  Reserved Bits (2),
  Packet Number Length (2),              /* Low order 2 bits of first byte */
  Version (32),
  Destination Connection ID Length (8),
  Destination Connection ID (0..160),
  Source Connection ID Length (8),
  Source Connection ID (0..160),
  Token Length (i),
  Token (..),
  Length (i),
  Packet Number (8..32),
  Packet Payload (8..),
}
```

***Short***


```
1-RTT Packet {
   Header Form (1) = 0,                /* High order bit of first byte */
   Fixed Bit (1) = 1,
   Spin Bit (1),
   Reserved Bits (2),
   Key Phase (1),
   Packet Number Length (2),           /* Low order bits of first byte */
   Destination Connection ID (0..160), //
   Packet Number (8..32),
   Packet Payload (8..),
}
```
Short используется для всех пакетов после того как сессионные ключи были установлены

*Кодирование номеров*
Короткий номер пакета -  пакеты могут начать повторяться. Длинный номер пакета - большой перерасход на передачу заголовка. 
Для кодирования пакетов в QUICK используется  *varint*. Длина *varint* кодируется первыми 2 байтами. 
```
00 - 2^6-1
01 - 2^14-1
11 - 2^62-1
```
QUICK **никогда** не разрешает посылать 2 пакета с одинаковым номером. Фактически, это означает, что QUICK соединение не может существовать вечно -  время от времени его надо будет перезапускать.

#### 0-RTT data
Иногда мы отравляем данные до завершения обмена ключей - точнее во время QUICK/TLS рукопожатие.  Такие данные называются 0-RTT. Для того чтобы защищенно обмениваться ключ или должен быть заранее обговорен, или  ключ был обговорен в прошлой сессии.
На практике это работает так:
1. Сервер во время предыдущей сессии посылает клиенту *TLS session ticket*. Это зашифрованная запись, которая содержит всю информацию, чтобы получив ticket сервер смог восстановить информацию о прошлой сессии. Далее этот тикет мапится в памяти сервера на адрес клиента
2. В следующем соединение клиент помещает тикет в *Client Hello*. Он использует ранее обговоренные ключи, чтобы зашифровать данные.
3. Сервер получает тикет, восстанавливает ключи, дешифрует данные
На картинке пример использовани
![[Pasted image 20260605172604.png]]

0-RTT опознаются в 1-RTT.
____
У 0-RTT в QUICK нет никаких защит. Если злоумышленник перехватит пакет, он сможет отправить его серверу еще раз. В определённых условиях это может быть очень плохо
