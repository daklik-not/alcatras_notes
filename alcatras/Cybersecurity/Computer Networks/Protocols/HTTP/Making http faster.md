Из-за появления real-time приложений, http должен быть быстрее.
**Первый прием - настройка серверов.**
Например HEAD методы и *If-Modified-Since* - клиенты проверяют, есть ли страницы в кэше.
Кэш можно использовать в сети.
Допустим, что какая-то группа часто обращается к одному и тому же сайту. Для такого случая часто создаются *прокси*-сервера. Прокси находится в сети группы. Все http запросы посылаются на прокси. Прокси проверяет, нет ли страницы у него в кэше. Также прокси можно использовать для блокировок каких-то веб-сайтов.
![[Pasted image 20260502012755.png]]
Есть *reverse proxy*. Допустим у сервера много запросов к базам данных. Чтобы оптимизировать, он поставит перед собой прокси сервер, который будет содержать кэш

*Spreading the Load*
Когда клиент обращается по домену он думает что общается с 1 сервером. На самом деле под 1 доменом может быть много серверов. Есть несколько подходов
1. Хранить каждый файл на каждом сервере. Выбор IP сервера скинуть на DNS протокол, например, round-robin, или географическая близость
2. Обратные прокси. Чаще всего они географически расположены близко к клиенту, и если страницы нет в кэше, то перенаправляют запрос на оригинальные сервера. Есть компании, который распределяют такие прокси по всей планете для кэширования веб-контента - *CDN*

**Второй прием - уменьшение времени, требуемого для получения веб-объектов**
Размер http страниц составляет примерно 2MB в среднем. Если загружать последовательно - сайт отобразится только, когда все будет подгружено. Используется *pipelining* - отправка множества запросов, не ожидая ответы. Значительно быстрее.

Главная проблема конвейера в том, что запросы не должны зависить друг от друга. Сейчас не используется
Другая проблема - ASCII. Я особо не понял, но по идее, неправильный запросы должны обрабатываться, что приводит к очень сложному коду парсера - к уязвимостям.

#### HHTP 2.0
Он отличается от HTTP/1.1
1. Используется бинарное кодирование, которые проще парсить и декодировать.
2. Поддерживается множество потоков, что дает возможность передавать данные по 1 каналу
3. HTTP/2.0 сжимает HTTP заголовки чтобы уменьшить количество передаваемых данных

![[Pasted image 20260502013109.png]]
1. *Length*- длина payload в байтах. $2^{24}$ максимальный размер.  Есть стандартный размер, $2^{14}$ его можно увеличить, если договориться вначале сессии через фрейм *Settings*
2. *Type* -  2 типа - данные и заголовки.
3. *Flags* - используются для некоторых типов фреймов.
4. *Stream Identifier* - c HTTP/2.0 битовый поток низлежащего транспортного уровня разбивается на независимые потоки, который идентифицируются числом. Нечетный поток - клиентом, четный - сервером.

**HTTP 2/0 Multilexing**
Благодаря мультиплексированию теперь можно делать вот так.  Передача длинных не блокирует короткие.

![[Pasted image 20260502013209.png]]
Из минусов, это усложняет реализацию - каждый фрейм должен обрабатываться по-своему для каждого веб-объекта. Эта сложность возникает на стороне клиента.

Первый кадр, который посылается - *Settings*. Он содержит некоторые параметры, предлагаемые клиентом на время сессии. Например *SETTINGS_MAX_FRAME_SIZE*(как минимум $2^{14}$) и *SETTINGS_MAX_CONCURRENT_STREAMS*(желательно 100).

Иногда сервер может отправить фрейм *in-advance* это свойство HTTP/2 называется *push*. Оно может работать только, если *SETTINGS_ENABLE_PUSH* был отправлен через *Settings* кадр клиентом. Классическое использование -  позволить серверу автоматически посылать обьект, который не может быть кэширован клиентом, вроде динамического js кода. Кстати в HTTP/3 его убрали)

На разные потоки можно устанавливать приоритеты через *Priority* кадры

У HTTP есть свой механизм контроля переполнения пользовательских буферов. *Window_update* кадр задает более большое окно получения. Это можно приложить к определенному потоку, или ко всему соединению. Стандартное - 65536 байт.

Есть и другие:
1. Ping - round-trip-time(но вообще вроде через icmp а не через http хз почему так написано)
2. GoAway - завершение HTTP/2.0 сессии.

**Determine Protocol Version**
Сервера должны уметь отличать HTTP1 от HTTP2.
Для этого первый запрос отправляется в HTTP/1.1 и выглядит примерно так:
```c
GET /robots.txt HTTP/1.1
Host: nghttp2.org
User-Agent: curl/7.52.1
Connection: Upgrade, HTTP2-Settings
Upgrade: h2c

HTTP2-Settings: AAMAAABkAARAAAAA
```
Сервер ответит вот этим:
```c
HTTP/1.1 101 Switching Protocols
Connection: Upgrade
Upgrade: h2c
```

Далее для подтверждения посылается HTTP/2.0rnrnSMrnrn, после нее следует SETTING фрейм, может быть пустым.
