TLS - Transport Layer Security. TLS работает поверх TCP. TLS отвечает за шифрование и аутентификацию SDU, которыми обмениваются приложения на прикладном уровне. TLS используется HTTP(HTTPS), SMTP, POP, IMAP.
TLS сессия может быть инициируема несколькими способами.
1. Отдельный TLS порт для каждого протокола прикладного уровня. Это не очень хорошо поскольку количество портов ограничивается.
2. TLS сессия начинается со специального сообщения. Например в SMTP - *STARTTLS*. 
```C
   STARTTLS
   220 2.0.0 Ready to start TLS
```

На веб-серверах TLS сессия сессия начинается сразу после установление TCP соединения.
TLS разделен на несколько стадий
1. TLS handshake
2. Data transfer

**Client Hello message**
Отправляется клиентом.
1. Версия TLS протокола. Сервер использует такую же версию или более старую
2. Рандомное число(nonce). Протоколы безопасности полагаются на случайные числа. Клиент посылает 32 битное рандомное число, где обычно 4 байта отвечают за часы клиента. Вместе с рандомным числом сервера, они используются для генерации ключа.
3. Список шифров(Cipher Suites) - список содержит набор криптографических протоколов, где самый лучший в начале: алгоритм обмена ключами, аутентификации, шифрования, хэширования.
4. Алгоритм сжатия. Написано что сжатие вместе с TLS работает плохо.
5. Расширения

*SNI*
Расширение TLS. На одном IP может жить сразу много доменов. Иногда хочется, чтобы у разных доменов были разные сертификаты. Именно для этого и указывается SNI - чтобы детектить сертификат.

**Server Hello**
1. ServerHello, которое содержит версию протокола, выбранную сервером, 32 случайных байта, выбранные сервером, CipherSuite выбранный сервером, полученный из списка предоставленным клиентом и сессионный ID. Сессионный ID нужен для идентификации сессии и параметров безопасности(например ключей). Он используется для восстановления сессии
2. Сертификат. Он связывает доменное имя на публичный ключ(каким-то образом я хз). TLS использует сертификат сервера, чтобы аутентифицировать сервер. Оно полагается на PKI - Public Key Infrastructure, которая состоит из набора корневых сертификационных центров, которые сертификационным центрам, которые выдают серверам. TLS клиенты часто сконфигурированы с ключами с публичными ключами некоторых корневых сертификационных центров, они используют эту информацию для валидации сертификатов сервера.
3. ServerKeyExchange - сообщение используется сервером для передачи информации, которая требуется для обмена ключами. Короче говоря она содержит выбранный алгоритм обмена ключами
4. ServerHelloDone - индицирует, что сервер отправил все сообщение для первой фазы рукопожатия
![[Cache/Pasted image 20260502015914.png]]
Важно заметить, что в TLS 1.3, фактически вся нужная информация содержится в ServerHello и ClientHello отлично от TLS2, который видимо тут рассматривается хз.
***TLS key exchange***
6. **RSA**. После того, как клиент подтвердил публичный ключ сервера, он может зашифровать рандомное число публичным ключом сервера, которое он дешифрует своим приватным. У сервера и клиента тогда есть секрет. Это число, а оно очень большое, можно использовать для выборки секретные ключи для шифрования и аутентификации данных. При таком подходе сообщение *Server Key Exchange* просто не нужно.
7. **DHE_RSA**. Работает, как классический DH. Параметры DH посылаются в сообщении ServerKeyExchange и подписывает их приватным ключом. Затем клиент продолжает обмен ключей и посылает свое вычисление ClientKeyExchange. Отличие от классического DH только в том, что первое сообщение посылается сервером.
*Perfect Forward Secrecy - PFS*
DHE_RSA намного безопаснее чем RSA. Представим ситуацию - кто-то все-таки смог получить доступ к приватному ключу сервера. Он полгода обменивался через RSA. Тогда он может расшифровать все сообщения за полгода. В DH каждый раз генерируется разный приватный ключ. Тогда человек сможет получить доступ только к текущей и будущим сессиям(подделать сертификат).
Сейчас используются *ECDHE_RSA* или *ECDHE_ECDSA*. 
***TLS Handshake ending***
Клиент посылает сообщение *ChangeCipherSpec*, и за ним finished. Это сообщение показывает, что клиент получил всю информацию, требуемую для генерации ключей безопасности. Также они используют чтобы индицировать смену алгоритма шифрования. Далее *Finished* - это первое зашифрованное сообщение. Оно говорит, о конце handshake и содержит хэш всех сообщений рукопожатия. Аналогично для сервера.

###  TLS record protocol
Теперь происходит обмен аутентифицированными и зашифрованными записями. Для разных криптографических протоколов разные форматы. Эти ключи выбираются из MasterSecret, который рандомно генерируется клиентом после RSA обмена, или выбирается из DH параметров.
Запись TLS всегда состоит из 4 различных полей:
1. Type - тип записи. Чаще всего *application data* - зашифрованные данные. Есть еще *handshake*, *change_cipher_spec* и *alert(намерение закрыть соединение)*.
2. Поле версии протокола, которое показывает версию TLS, которую используется протокол. 2 числа major и minor числа. Major - смена версии(нет обратной совместимости). Minor - подверсия - есть обратная совместимость.
3. Length поле. $length < 16384bytes$
4. TLSPlainText-  зашифрованные данные.

Рассмотрим, например, *Stream Encryption*.
Сначала надо вычислить код аутентификации, чтобы подтвердить целостность данных. Вычисляется MAC #MAC  - $MAC(SeqNum, Header, PlainText)$, используя HMAC, где SeqNum увеличивается после отправки каждой записи. SeqNum нужно чтобы предотвратить replay атаку.
В современных протоколах (TLS 1.3) используется encrypt-then-mac - данные сначала шифруются, потом по ним вычисляется MAC.

### Improving TLS
Сейчас большая часть трафика идет через TLS. Для шифрования чаще всего используется AES - RSA слишком медленный + у AES есть аппаратная поддержка. RSA до 2012 использовался для обмена ключами. Сейчас в 90% случаев используется ECDHE. 
Достаточно сложно было развертывать TLS сервера - сисадмин должен был выдать сертификаты и сконфигурировать список серверов. Сейчас есть множество сайтов, которые предоставляют TLS сертификаты веб-сайтам.

***TLS 1.3***
Большой проблемой TLS 1.2 была задержка - нужно было пройти как минимум 4 round-trip-time - создание TCP соединений, обмен Client/ServerHello, обмен ключами,  и только потом GET запрос. TLS 1.3 уменьшил все это дело до 1 round-trip-time. TLS 1.3 использует небольшое число шифров, при этом `TLS_AES_128_GCM_SHA256` обязательный. Все шифры, которые не поддерживают PFS были убраны. Сжатие также было убрано.
TLS 1.3 рукопожатие сильно отличается от TLS 1.2. Во-первых, TLS 1.3 рукопожатие требует только 1 round-trip-time, когда клиент впервые подключается к серверу. TLS 1.3 упрощает эти договоренности, требуя использовать DH c небольшим изначальным набором параметров - а именно угадать p и g.
![[Cache/Pasted image 20260502020953.png]]
Есть несколько важных отличий от TLS 1.2 рукопожатия. Изначально DH обмен ключами требуется TLS 1.3 и этот обмен инициируется клиентом. Клиент должен просто угадать p и g, которые почти всегда одинаковы для всех участников. Тогда обмен ключами начинается сразу же. Таким образом после ServerHello все сообщения идут зашифровано(красные на рисунке). Клиент проверяет сертификат и посылает зашифрованный *Finished*.
