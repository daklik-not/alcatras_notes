#rpc
Иногда хочется чтобы процедуры программы были выполнены не на искомом хосте - *remote procedue calls*. На этом принципе построено множество распределенных систем.
Стандартная модель выполнения де-факто описана в заметках про ОС. Просто передаем управление процедуре, если она блокирующая.
2 проблемы при удаленных вызовах - нет общей памяти, разное кодирование данных
#### Encoding
Несмотря на то что, много кодировок зафиксированы в стандартах, многие приложения используют свои особенные кодировки. 
Есть 3 популярных метода кодировки - *XML, JSON, XDR*.

**XDR**
Показывает, как данные кодируются перед отправкой. Простые типы данных кодируются как есть, например int, просто 4 байта. Булев тип данных оборачивается в int. Для чисел с плавающей точкой стандарт IEEE:
![[Cache/Pasted image 20260502013753.png]]

Короче смысл примерно такой, что у нас есть число, мы с помощью $S$ - флага, который показывает отрицательное или положительное число. $E$ - экспонента числа $2^{E-x}$, $F$ - часть $1.F$.
Тогда число высчитается по следующей формуле:$$(-1)^S * 2^{E-1023} * 1.F$$
Я особо не разбирал, но оно опирается на свойства представления чисел через экспоненту.

Также поддерживаются комплексные типы данных, например байтовая строка
Первая часть длина, вторая последовательность байт. Должно быть кратно 32 битам - добавляются padding биты.

***JSON***

**Integer**  
представление: последовательность ASCII цифр  
примеры: 123, 0, -456  
примечания: минус только в начале, без ведущих нулей

**String**  
представление: в двойных кавычках " "  
примеры: "hello", "", "123"  
примечания: всегда в кавычках, пустая строка — ""

**Boolean**  
представление: true или false  
примеры: true, false  
примечания: только нижний регистр, без кавычек

**Разделитель**  
представление: запятая между полями  
примеры: true, "text", 42  
примечания: пробелы после запятой опциональны

#### Reaching the callee
Нужно убедиться, что хост к которому обращаемся слушает на определенном порте. Это используется в *JSON-RPC* - легкий протокол, не зависящий от низлежащего транспортного уровня протокол удаленного вызова процедур, использующий JSON.

| Название | Описание                            |
| -------- | ----------------------------------- |
| jsonrpc  | версия протокола                    |
| method   | имя процедуры                       |
| params   | параметры, передаваемые <br>в метод |
| id       | идентификатор выбранный вызывающим  |

```c
{ "jsonrpc": "2.0", "method": "sum", "params": [1, 3], "id": 1 }
```

После получения вызова callee разспарсивает его и также посылает ответ в JSON

| Название | Описание                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| jsonrpc  | версия протокола                                                                                                                                                      |
| id       | идентификатор выбранный вызывающим                                                                                                                                    |
| result   | результат процедуры                                                                                                                                                   |
| error    | заменяет result. Содержит<br>1) code: число показывающее тип ошибки<br>2) message: строка с коротким описанием ошибки<br>3) data: дополнительная информация об ошибке |
```c
{ "jsonrpc": "2.0", "result": 4, "id": 1 }
{ "jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": "1" }
```

Id важна для того, чтобы не возникало проблемы с потерянными респонсами, из которых вытекает повторение операции. Чаще всего вообще используют удаленный процедуры, которые могут быть использованы много раз, не ломая логику операции.

***ONC-RPC***
$2^{16}$ - ограниченное число портов. Тогда невозможно каждой процедуре дать свой порт. В *ONC-RPC* используется *portmapper*. Она запущен на стандартном порте. Сначала клиент обращается к portmapper, чтобы узнать к какому порту ему обращаться. И только после этого идет на порт.

PS: Согласно Deepseek, JSON-RPC чаще всего используется в интернете. Проблема с портами решается тем, что все процедуры должны находиться в 1 приложении, к которому через порт будем обращаться
