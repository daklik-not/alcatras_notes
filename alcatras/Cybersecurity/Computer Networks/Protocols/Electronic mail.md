В CSRF атаке пользователь делает запрос с плохого сайта на хороший. Запрос содержит данные пользователя и приводит к тому, что сервер делает какие-то плохие действия, думая, что их вызвал пользователь

  

#### Обзор

Чтобы подтвердить пользователя, когда он делает запрос к серверу, он должен предоставить удостоверение, например сессионные куки.  Пример

Запросы, за которыми следует действие называются *state-changing requests*

В CSRF атаке на плохом сайте есть форма, которая вызывает запрос к другому сайту, как в коде

```c

<form action="https://my-bank.example.org/transfer" method="POST">

  <input type="hidden" name="recipient" value="attacker" />

  <input type="hidden" name="amount" value="1000" />

</form>

И потом форма сразу отправляется:

const form = document.querySelector("form");

form.submit();

или

<img src="https://my-bank.example.org/transfer"/>

```

Проблема в том, что такой запрос может автоматически отправить куки пользователя для хорошего сайта, и тогда действие, которое записано в форме плохого сайта выполнится, поскольку пользователь подтвердится.

### Защиты от CSRF

#### CSRF токены

Когда мы делаем к сайту GET запрос, сервер зашивает в страницу специальные рандомизированные данные - **CSRF токен**.  Смысл в том, что злой сайт, отправляя форму не знает **CSRF-токен** ведь у него нет страницы, к которой он обращается.

Возникает вопрос, почему он не  может просто сходить на этот сайт и получить токен. Он не может прочитать сайт из-за Same-Origin-Policy.

В фреймворках можно защищать с помощью CSRF токена. Токены размещаются в hidden поле формы, в куки, и тд.

CSRF токены нужно помещать везде, где есть запросы изменения состояния, вроде банковского перевода.

#### Fetch metadata

Набор HTTP заголовков, добавленных браузером, которые обеспечивают доп-информацию о контексте HTTP запроса.

Самый частый -  Sec-Fetch-Site, который говорит какой запрос - same-origin, same-site, cross-site, или вызван напрямую. Пример в коде

```c

app.post("/transfer", (req, res) => { // это обрабочик POST запросов.

  const secFetchSite = req.headers["sec-fetch-site"];

  if (secFetchSite === "same-origin" || secFetchSite === "same-site") {

    console.log("allowed");

    // Update state

  } else {

    console.log("denied");

    // Don't update state

  }

});

```

  

#### Избегать простых запросов

Простые запросы могут быть сделаны cross-origin без блокирования. (про них будет в заметке про CORS). Со сложными запросами так нельзя - вроде используется *preflight*. Можно все  *state-changing* запросы трактовать как сложные. Например, если превращать тело POST запроса в JSON - body: JSON.stringify({ recipient: "joe", amount: "100" }). Или можно добавлять какой-то кастомный заголовок - тогда тоже будет как сложный.

  

**Непростые запросы и CORS**

CORS не позволяет сложным запросам даже отправлятся *cross-origin*. Чтобы это было не так строго можно облегчить с помощью заголовков -Access-Control-Allow-Origin,, Access-Control-Allow-Credentials

### Передача данных через email.
Когда Алиса посылает сообщение Бобу, она подготавливает свое email сообщение через email клиент. Чтобы послать сообщение используется **SMTP** протокол, чтобы послать на свой SMTP сервер. Сервер Алисы должен найти SMPT сервер, который содержит почтовый ящик Боба. Это делается через *Maxil Exchange(MX)* записей DNS. Каждая MX запись содержит числовой приоритет и доменное имя SMTP сервера, который может отправить сообщение. SMTP сервер будет хранить сообщение, пока Боб не получит его, используя свой email используя протоколы вроде *IMAP* и *POP*.

#### The simple Mail Transfer Protocol
Это текстовый клиент-серверный протокол. 

Email сообщение создаются на *Mail User Agent - MUA*.  Это email клиент или почта. MUA посылает сообщение на *Mail Submission Agent* - MSA. MSA обрабатывает полученный Email и отправляет его на *Mail transmission agent* - MTA.  MTA отвечает за передачу сообщения напрямую или через посредние MTA. MTA отправит сообщение на *Mail Delivery Agent* - MDA, где его получить MUA получателя.

SMTP используется для MUA-MSA, MSA-MTA, MTA-MTA.

Передача сообщений происходит в 3 фазах.
1. Клиент открывает транспортное соединение с сервером. После установления посылается команда EHLO.
2. Email фаза. Клиент передает 1 или более сообщений через MAIL FROM команду, RCPT TO команду и DATA команду
3. QUIT - завершение сессии.
   
Пример
```c
S: 220 smtp.example.com ESMTP MTA information
C: EHLO mta.example.org
S: 250 Hello mta.example.org, glad to meet you
C: MAIL FROM:<alice@example.org>
S: 250 Ok
C: RCPT TO:<bob@example.com>
S: 250 Ok
C: DATA
S: 354 End data with <CR><LF>.<CR><LF>
C: From: "Alice Doe" <alice@example.org>
C: To: Bob Smith <bob@example.com>
C: Date: Mon, 9 Mar 2010 18:22:32 +0100
C: Subject: Hello
C:
C: Hello Bob
C: This is a small message containing 4 lines of text.
C: Best regards,
C: Alice
C: .
S: 250 Ok: queued as 12345
C: QUIT
S: 221 Bye
```

#### Post Office Protocol - POP
Сначала на университетских компьютерах, который принадлежали куче пользователей, приходящий email просто клался в нужную папку пользователя. Использовался только протокол TCMP.  Все хосты запускали SMPT сервер. С использованием ПК все поменялось.
Можно было подключаться к серверу через telnet и просить отправить сообщение - но это не user-friendly. Потом появились клиентские приложения, которые сами могли получать сообщения от пользователя с сервера.

Самый простой - POP. Также есть IMAP - он позволяет читать письма с сервера не скачивая их к себе.

POP сервер слушает порт 110
POP сессия состоит из 3 частей - авторизация, транзакция, обновление(вывод по сессии я хз).
