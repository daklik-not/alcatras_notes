
TCP основан на окне и обеспечивает обслуживание двухстороннего байтового потока.
Есть 3 поля:
1. *sequence* number - в этом случае содержит порядковый номер первого байта данных сегмента
2. *acknowledgment* number - содержит номер следующего байта, который сервер ожидает получить.
3. window - текущий размер окна отправителя

***TCB***
Для каждого соединения создается TCB - Transmission Control Block. Стоит сказать, что это структура ядра, к которой нет прямого доступа у пользовательских программ. Для доступа через терминал нужны специальные программы.
Здесь есть все поля: локальный IP, удаленный IP, локальный и удаленный номера портов, текущее состояние TCB, MSS.
Из интересного:
1. snd.nxt - порядковый номер следующего байта в байтовом потоке.
2. snd.una самый ранний порядковый номер, который был послан, но еще не опознан.
3. snd.wnd - текущий размер окна отправки в байтах.
4. rcv.nxt - последовательный номер следующего байта, который ожидается быть полученным от удаленного хоста. Всегда установлен в первый не пришедший байт.
5. rcv.wnd - размер окна, представленного удаленным хостом
6. sending buffer - все неопознанные данные
7. receiving buffer - все полученные данные, еще не отправленные пользователю.
PS: ***оказывается в спецификации на других местах rcv.wnd и snd.wnd***. В рамках этой заметки я ничего не буду менять, но так, лучше об этом помнить.
***Отправка данных***
Чтобы отправить данные по установленному соединению, сначала проверяется, что *sending buffer < rcv.wnd*. Это значит, что мы можем отправить еще какие-то данные. Далее, до MSS байтов кладется в *payload* TCP сегмента. *Sequence* число сегмента это первый байт payload -  *snd.nxt*. Сам *snd.nxt = snd.nxt + payload.length()*. *Acknowledgment* число устанавливается в текущее значение *rcv.nxt*.  После winow высчитывается из буфера получения.

Когда приходит TCP сегмент с ACK, то rcv.wnd устанавливается в значение window. Таким образом мы контролируем, сколько данных мы можем отправить на удаленных хост. Номер опознавания сравнивается с *snd.una*. Таким образом мы понимаем, сколько данных дошло.  Опознанные данные убираются из буфера и snd.una обновляется.  Если сегмент содержит данные, то *sequence* число сравнивается с *rcv.nxt*.  Если они равны, то сегмент был полностью получен и rcv.nxt обновляется. 

**Segment Transmission Strategies**
Можно отправлять каждый байт отдельно, и оборачивать его в заголовок. Но это очень неэффективно Можно чтобы байты отправятся только, когда накопится MSS байтов. Все байты оборачиваются в сегменты. Это может привести к очень большим задержкам доставки данных
*Nage Algo*
Было предложено следующее решение:
```c
if rcv.wnd >= MSS and len(data) >= MSS:
    send one MSS-sized segment
else:
    if there are unacknowledged data:
        place data in buffer until acknowledgment has been received
    else:
        send one TCP segment containing all buffered data (up to rcv.wnd
```

***TCP Windows***
Большое ограничение оригинального TCP - 16 битное окно - размер окна всего 65535 байт. Поле windows содержит всего 16 бит. Чтобы решить это, в заголовке будем хранить $snd.wnd >> S$, где S договаривается в начале соединения через TCP опции в сегментах SYN. Если сервер не поддерживает это, он просто игнорирует эту опцию.
Сегодняшние реализации могут сами расширять размеры окна отправки/получения чтобы поддерживать более хорошую пропускную способность.
