### TCP retransmission timeout
Если таймаут слишком маленький - много сообщений которые были корректно доставлены, но просто не успели дойти
Если таймаут слишком большой, то пропускная способность тратится поскольку если не приходит опознавание - долго ждать.
Чтобы определить таймер нужно знать round-trip-time. Нельзя оценить время между отправкой сегмента и получением опознавания, поскольку есть потери данных.
Для этого была добавлена *timestamp* опция.
1. TSval - устанавливается отправителем сегмента
2. TS Echo Reply - последнее TSval, полученное от удаленного хоста и сохраненного в TCB

Короче смысл в том, что если TSecho полученного отличается от TSval отправленного, то это ретрансмиссия и такое оценивать не надо.
PS: Sequence числа могут переполниться за 1 соединение. Тогда будет 2 сегмента с одинаковыми порядковыми числами. Чтобы их различать будем ассоциировать с каждым сегментом timestamp

Далее мы можем посчитать нужный timeout. Он меняется. Изначальный в 3 секунды.
**Оригинальная спецификация - плохо работает** 
1. $srtt = (a * srtt) + ((1 - a) * rtt)$, где $srtt$ - оценка rtt с помощью экспоненциального сглаживается, $rtt$ - время посчитанное с помощью timestampов. Такая же формула использовалась в *shortest process next* в алгоритмах планирования
2. $rto$ - таймаут ретрансмиссии вычисляется как $rto = min(60, max(1, \beta * srtt))$

**Алгоритм Якобсона - актуальная реализация**
Изначально:
1. $srtt = rtt$
2. $rttvar = rtt / 2$
3. $rto = srtt + 4 * rttvar$

Далее:
1. $rttvar = (1 - \beta) * rttvar + \beta * |(srtt - rtt)|$
2. $srtt = (1 - a) * srtt + a * rtt$
3. $rt0 = srtt + 4 * rttvar$
4. $a = 1/8, \beta = 1/4$

## Advanced retransmission strategies
Первое - есть экспоненциальное увеличение таймаута ретрансмиссии - после каждой время ретрансмиссии удваивается - это помогает не забивать пропускную способность ретрансмиссиями. Максимальный таймаут 60 секунд - после него считается что хост недостижим. 
**Piggybacking**
*Piggibacking* - когда опознавание посылается с другим сегментом. Чаще всего используется *delayed ack* стратегия.
```c
#Здесь типо асинхронный код, который не очень понятно работает.
reception of a data segment:
    if pkt.seq == rcv.nxt:  # segment received in sequence
        if delayed_ack: #то есть если запущен таймер на первый сегмент, а приходит еще один целый, то для первого сразу отправляется чистый ack.
            send pure ack segment
            delayed_ack = False
            ack_timer.cancel()
        else: #а если никого нет на таймере, то запускаем свой таймер
            delayed_ack = True
            ack_timer.start()
    else:  # для поврежденного сразу отправляем ACK
        send pure ack segment
        if delayed_ack:
            delayed_ack = False
            ack_timer.cancel()

transmission of a data segment:  # piggyback ack
    if delayed_ack: # если есть таймер цепляем
        delayed_ack = False
        ack_timer.cancel()

acktimer expiration: # отправляем обычный сегмент
    send pure ack segment
    delayed_ack = False
```
***TCP With Selecting Repeat -SACK***
#selective_repeat 
Когда много потерь *go-back-n* плохо работает. В TCP были добавлены расширения, которые позволяют использовать *selective repeat*  - все сегменты полученные не по порядку будут просто буферизироваться
Есть *изолированные потери сегментов*. Это когда 1 большой поток и в нем придет 1 некорректный сегмент. Тогда все что отправилось после него придется отправлять заново. Это медленно. *selective-repeat* позволяет не перенаправлять все, а только потерянный. 
*fast retransmit heuristic*
Если есть selective repeat, то сегменты продолжают отправляться, несмотря на некорректное число для предыдущего. Есть проблема(и там и там). Мы не умеем отличать изменение порядка прихода сегментом на получателя и потерю сегмента.  Пакет 1 **потерялся в сети** или он просто **задержался и придёт позже**?
![[Pasted image 20260502023921.png]]
Чтобы различать их, придумали, что будет делать ретрансмиссии только когда приходи 3 опознавания.
*fast retsransmit* эвристика хорошо работает в средах, где много изолированных потерь сегментов. В таких средах нужно включать *selective repeat TCP*.  Используется **SACK** опция. Она позволяет TCP получателю показать блоки, который он получил, но вне порядка.
![[Pasted image 20260502024002.png]]
В SACK опции может быть много блоков - обычно не более 3. Когда блоков в буфере больше - надо выбирать. Хорошая эвристика - выбирать блоки, которые недавно были изменены.
Можно использовать аналог *fast retransmit* - перенаправлять только после 3 SACK с этой дырой. SACK не заменяет ACK.
