Есть несколько типов атак, связанных с DNS
#### Eavesdropping - подслушивание
Атакующий может захватывать пакеты, посланные на резолвер или DNS сервер может получить важную информацию о DNS имена, которые используются конечным пользователем. Атакующий узнает к каким адресам обращается пользователь
#### MITM-атака
На практике тяжело реализовать, поскольку резолверы находятся в защищенных местах. Но если атакующий контролирует точку доступа пользователя, то он может легко модифицировать пакеты, в том числе и DNS пакеты

Если атакующий не может контролировать путь до роутера. 
Первое поле любого DNS запроса - *id*. Ответ DNS сервера используется только если идентификатор от сервера и от пользователя совпадают.
Теперь представим, что атакующий предугадал сайт, к которому обращается Алиса. Он может перебрать все идентификаторы с предугаданным сайтом и послать от имени того сайта неправильный ответ. 
С другой стороны Мэллори нужно посылать пакеты от имени DNS резолверы - в хороших сетях это будет заблокировано.
Это особенно опасно, если у DNS большой TTL(время жизни)

Придумали защиту от этой атаки. DNS передается в UDP сегментах. Будем использовать разный UDP порт для каждого DNS запроса(реально разный кстати в wireshark проверил). Это увеличивает перебор с $2^{16}$ до $2^{32}$. 

Еще атака. Часто в 1 DNS ответе отправляется сразу несколько записей.  Так, например, для *NS* записи.  В запросе для записи NS, мы получаем в ответе имя  DNS сервера, который обслуживает запрашиваемый домен, и сам IP сервера. Некоторые DNS сервера возвращают нескольку NS записей и связанные IP адреса. 
Пример: Мэллори заставляет зайти Алису на его сайт. Алиса посылает DNS запрос. DNS сервер, который отвечает за сайт Мэллори, и который контролирует сам Мэллори. В ответе Мэллори отправляет условно *google.com -> mallory_ip*. Теперь пока TTL записи не истечет, то Алиса будет обращаться к Мэллори вместо гугла.

*DNSSEC*
Расширения для DNS. Использует криптографию по публичному ключу для аутентификации DNS.  С DNSSEC каждая DNS-зона использует свою пару private-public ключей.
Определяется 4 новых типа DNS записей
1. DNSKEY запись позволяет хранить публичный ключ, связанный с зоной и идентификатор алгоритма публичного ключа(что дает поддержку нескольких алгоритмов)
2. RRSIG - сигнатура DNS записи. Есть доп-поля - алгоритм, использованный для сигнатуры, идентификатор публичного ключа(дипсик написал, что эта штука нужна для фильтрации), TTL, период, пока сигнатура будет валидна.
3. DS - хэш публичного ключа - сертификация публичного ключа одного из своих детей.
4. NSEC позже

Чтобы получить аутентифицированную запись, резолвер Алисы должен сначала получить NS, который в ответе за .org TLD(Top Level Domain). Это обслуживается корневым сервером DNS и резолвер Алисы может извлечь сигнатуру для этой NS записи. Поскольку Алиса знает DNSKEY корня она может подтвердить сигнатуру.

Следующий шаг - обратиться к *ns.org*.  Полученная запись также сопровождается *RRSIG*. Ключ передается через DNSKEY. Чтобы проверить ключ выстраивается следующая цепочка. Мы обращаемся к корню, которому доверяем, после чего запрашиваем от него *хэш публичного ключа  дочернего DNS* к которому мы хотим обратиться. От ключа, полученного в DNSKEY вычисляется хэш и сравнивается с уже посчитанным. Если сходятся - то DNS доверенный. Когда будет обращаться к уже его ребенку, то DS будет подписываться уже ключом этого DNS сервера.
Ключ которому мы доверяем называется *anchored key*

*Детали*
Все RRSIG записи могут быть вычислены оффлайн, не в режиме реального времени.  Нельзя заставить в онлайн DNS сервер вычислять сигнатуры + даже если будет доступ к серверу, не будет доступа к ключам. Когда DNS сервер кэширует записи, он меняет TTL на новый. Из-за этого меняется RRSIG -> нужно пересчитывать хэш. Резолвер меняет временно на оригинальный TTL + проверяется, что Полученный TTL < оригинальный TTL. Validity период нужен для того, что ключи сами по себе истекали во времени - полезно при замене ключей.

*NSEC*
Нужно, чтобы аутентифицировать негативные ответы. Они тоже кэшируются. Мы хотим чтобы они тоже вычислялись онлайн. Для этого будет использовать.
```c
alpha.example.org
alpha.example.org NSEC beta.example.org

beta.example.org
beta.example.org NSEC gamma.example.org

gamma.example.org
gamma.example.org NSEC alpha.example.org
```
Пример: если обратиться к delta.example.com, то он вернет gamma.example.org NSEC alpha.example.org
Таким образом резолвер логически поймет, что между записями ничего нет -> такой записи нет
