DATA.req / DATA.ind - взаимодействие между пользователем и datalink уровнем.
send / recvd - взаимодействие между подуровнем, отвечающим за кадрирование и datalink уровнем. Этот уровень занимается поиском и формированием фреймов.

____
**SDU** - любые данные передаваемые по протоколу
**Service** - то, что предоставляется верхнему уровню - часто интерфейс. send(SDU)- относится к сервису
**Протокол** - реальная реализация. Например, как framing подуровень реализует бит-стаффинг.
___

Когда сущность канального уровня запущена на идеально работающей framing подуровне, то она может просто вызывать send(SDU) сразу после DATA.req(SDU), аналогично для получения.

Есть несколько проблем с таким подходом. Первое - сервер может быть медленнее чем устройство - он может просто не успевать принимать данные. Второе - физический канал может быть медленнее, чем количество поступаемых данных. Для этого у сущности канального уровня есть буфер, но он может переполниться. Тогда ОС приостановит приложение. Аналогично с полученными кадрами.

Что бы решить эту проблемы отправитель должен поддерживать обратную связь с получателем. Тогда протокол должен обрабатывать два типа кадров
1. Кадры с данными, несущие SDU
2. Кадры управления, несущие информацию о том, что предыдущий фрейм был успешно обработан

Чтобы их различать кадры разбиваются на 2 части:
1. Заголовок, где бит 0 - кадр данных, бит 1 - кадр управления
2. Сами данные
Короче теперь все будет происходить как на картинке. Основная идея в том, что получатель сам решает когда ему можно отправить данные
