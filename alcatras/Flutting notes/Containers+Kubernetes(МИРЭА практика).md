Начну с того, что вообще такое контейнер. Контейнер - процесс, который изолирует тот или иной компонент информационной системы. Зачем это надо? В первую очередь это решает проблему версионирования - для каждого компонента системы в адресном пространстве контейнера находится нужная ему версия чего-бы то ни было - dll библиотеки, питона, nodejs.  Во-вторых поломка одного контейнера не сломает другой, например если отвалится фронт, то бэкэнд продолжит обеспечивать работу к API. 
Теперь про то, как имененно осуществляется изоляция. Используется специальный механизм операционной системы - **namespace**.

Чтобы структурировать все свои файлы для контейнера используется **image**. Это архив, Который содержит все файлы, которые нужны для запуска контейнера.  Очевидно, что архивы нельзя менять. 
Image состоит из слоев. Изначально слой это просто папка, которая лежит в специальной папке, которая называется локальным хранилищем докера.  Когда мы собираем image, docker смотрит, а может у меня уже есть в кэше слой, который мне тут нужен. Если он есть то docker для нового image просто возьмет из кэша. В этом главное преимущество слоев: не надо заново скачивать что уже  есть. 
На первом слое докера чаще всего находится пользовательская часть операционной системы, например системные папки(/etc,/lib) - это надо для минимальной работы, поскольку программам чаще всего нужны  пользовательские системные библиотеки, например libc. 
Когда docker-image запускается:
```
*docker run --name=base-container -ti ubuntu* // что то такое 
```
то сначала скачиваются все нужные слои в кэш, после чего создается файловая система, где слои размещаются 1 поверх другого.
Процесс запуска происходит следующим образом. Используется специальная OverlayFS. Она смотрит на слои,  и накладывает их так друг на друга что в результате получается единая папка: Пример:
```
mkdir -p /tmp/demo/lower1
mkdir -p /tmp/demo/lower2
mkdir -p /tmp/demo/upper
mount -t overlay overlay \
      -o lowerdir=/tmp/demo/lower2:/tmp/demo/lower1,\ // иерархия, что на что будет накладываться 
         upperdir=/tmp/demo/upper,\ // измененные файлы будут класться сюда
         workdir=/tmp/demo/work \  
      /tmp/demo/merged // точка монтирования, куда скинутся файлы после сборки
```

root директория устанавливается в chroot.
Регистр это где хранятся репозитории с image.

### Kubernetes - Платформы оркестрации
Собственно говоря, в сложных системах появляется много контейнеров, на разных виртуальных машинах. Тогда встает вопрос, а как вообще таким количеством контейнеров управлять. Представим, что одна служба, например бэкенд сильно загружено. Неплохо было бы выделить ей ресурсов операционной системы, или вообще создать дополнительный контейнер. Для таких случаев придумали платформы оркестрации системы. Они позволяют:
1. Балансировка нагрузки, например распределение сетевого трафика между контейнерами
2. Быстро настраивать доступ к хранилизщу для всех контейнеров.
3. Восстановление
4. Выдает IP адреса специальным POD(грубо говоря группа контейнеров, отвечающих за 1 задачу). Системы орестрации позволяют общаться 1 системе, даже есть каждый POD на разном устройстве через TCP/IP?

Среди платформ оркестрации  абсолютно доминирует Kubernetes. 

***Архитектура***
То чем управляет кубернетес называется кластер. Кластер это грубо говоря куча компов. Когда кластер управляется кубернетесом он внезапно становится **Kubernetes cluster**.
Каждая рабочая машинка называется нодой, на ней запущены контейнеры.  ***Control plane*** - программы которые управляют рабочими нодами в кластере. Чаще всего запущен на множестве компов. ![[Pasted image 20260907163219.png]]
https://kubernetes.io/images/docs/kubernetes-cluster-architecture.svg
***Control plane components***
Рассмотрим основные элементы контрольной плоскости кластера кубернетес.
1. kube-apiserver. Он валидирует и конфигурирует данные для API обьектов - PODS(набор контейнеров), сервисы и другие
2. etcd - настройки конфигурации. kube-apiserver идет к etcd, получает оттуда настройки, после чего идет к самой ноде, которую надо настроить
3. kube-scheduler. когда kubeapi-server хочет создать под, он размещает эту настройку в etcd, после чего оттуда ее считывает kube-scheduler. Он записывает номер выбранной ноды, на которой запустится под.
4. kube-controller-manager. KCM использует KAP для получения данных с etcd. Оттуда он получает желамое состояние системы(пользовательскую команду) и текущее. Далее он решает что именно нужно сделать, чтобы состояние стало желаемым. Далее он осуществляет это через KAP
5. cloud-controller-manager. Компонент, который встраивает cloud логику. 

***Node components***
1. kubelet. занимается разворачиванием POD на конкретной ноде.
2. kube-proxe. позволяет устройствам общаться по сети.

### Docker Swarm
Если не углубляться в детали докера, то есть Docker Engine. Он состоит из docker демона(сервер), который всем управляет. REST API - то через что приложение общается с демоном и docker cli  - пользователь через нее отправялет команды управления. 
В Docker Engine встроена система оркестрации - ***Swarm***. 
***Архитектура***
Вводится абстракция **Docker Host** - компьютер на котором установлен docker engine. Заданный докер хост может быть *manager*, *worker* или и тем и тем.  Благодаря Docker Swarm можно менять конфигурацию и настройки всех докер контейнеров
